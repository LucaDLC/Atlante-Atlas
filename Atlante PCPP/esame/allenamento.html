Lezione 1 · Concorrenza e mutua esclusione

1 · What kind of concurrency is requesting a web page from a server?

Riquadro blu, lezione 1.

Risposta modello

"It depends on the point of view. For the client it is inherent concurrency: the browser must stay responsive to the user while it waits for the network. For the server it is hidden concurrency, because many requests share the same machine and each behaves as if it had the server for itself, and exploitation if the server uses several cores to serve more requests."

Le categorie non si escludono: conta il motivo. Perché la concorrenza.

2 · Two threads each execute counter++ 3 times without locks. What is the minimum value the program can print?

Riquadro blu "HARDer", esercizio 1.1.8.

Risposta modello

"2, not 3. t1 reads 0 and is paused. t2 does two full increments. t1 writes 1, overwriting t2's work. t2 then reads 1 and is paused. t1 finishes its remaining increments. t2 finally writes 2, overwriting everything t1 did. So the last write is 2."

Verificato enumerando tutti gli interleaving: interleaving.

3 · What is a race condition? What is a critical section?

Risposta modello

"A race condition occurs when the result of a program depends on the interleaving of the threads, for example when two threads increment a shared counter and one update is lost. A critical section is the part of the code that accesses shared state and must be executed by at most one thread at a time. Mutual exclusion is the property that no two threads are in the critical section at the same time, and we ensure it with locks."

4 · Why do we call unlock() in a finally block?

Risposta modello

"If the critical section throws an exception, the code after it is skipped. Without finally the lock would never be released, and every other thread calling lock() would block forever. The finally block runs in every case, so the lock is always released."

5 · A thread holding a ReentrantLock calls lock() on it again. What happens?

Risposta modello

"It succeeds immediately, because the lock is reentrant: the lock records its owner and a hold count, which goes to 2. The thread must call unlock() twice before other threads can acquire it. Intrinsic locks (synchronized) are reentrant too; a semaphore is not."

Lezione 2 · Monitor, fairness, visibility

6 · Why must await() be called in a while loop and not in an if?

Risposta modello

"Java monitors follow Mesa semantics: a signalled thread is only moved back to compete for the lock, it does not run immediately. By the time it reacquires the lock, another thread may have changed the state, so the condition may be false again. Threads can also wake up spuriously. The while loop re-checks the condition after every wake-up."

Mesa e Hoare.

7 · Is the readers-writers monitor fair towards writers? How do you fix it?

Esercizio 2.1.2.

Risposta modello

"No. A writer waits until there are no readers, but new readers can keep entering while others are still reading, so the number of readers may never reach zero and the writer starves. The fix is a flag set by a waiting writer: new readers must wait while the flag is set, so the current readers eventually leave and the writer enters."

Limite da dire: la scelta di chi prende il lock resta arbitraria se il lock non è fair. Fairness.

8 · Why do visibility problems occur?

Riquadro blu, lezione 2.

Risposta modello

"Each core has caches and registers, and a write may stay there for a while before reaching main memory; compilers and CPUs may also reorder instructions. Without synchronization, nothing forces a write of one thread to become visible to another thread, so a thread may keep reading a stale value, for example looping forever on a flag."

Visibility.

9 · What are the possible outputs of PossibleReordering?

Riquadro blu, lezione 2. t1: a = 1; x = b; · t2: b = 1; y = a;

Risposta modello

"(0,1), (1,0) and (1,1) come from interleavings. (0,0) is also possible: it is not produced by any interleaving, but by reordering or visibility effects, since the writes and reads are not ordered by happens-before."

10 · Mystery: all methods are synchronized, so why is there a race condition?

Esercizio 2.3.

Risposta modello

"A synchronized instance method locks this, a static synchronized method locks the class object. They are two different locks, so an instance method and a static method can update the static field sum at the same time: there is no mutual exclusion between them."

synchronized.

Lezione 3 · Java Memory Model

11 · Why do we need a memory model?

Riquadro blu, lezione 3.

Risposta modello

"Hardware differs between machines, and compilers, runtimes and CPUs optimise code in ways that produce non-sequentially-consistent results. The Java memory model is a set of rules defining which executions are valid on any hardware, so programmers can predict the behaviour of their programs. It guarantees sequential consistency for correctly synchronized programs."

12 · Name the happens-before rules.

Risposta modello

"Program order within a thread; the monitor rule (an unlock happens-before every subsequent lock on the same monitor); the volatile rule (a write to a volatile variable happens-before every subsequent read of it); the thread start rule (start() happens-before the first action of the started thread); the thread termination rule (the last action of a thread happens-before a join() on it); and transitivity. The lecture notes list the complete set with the default initialization rule."

Le otto regole.

13 · When does a program contain a data race?

Risposta modello

"When an execution contains two conflicting actions, that is, two accesses to the same non-volatile variable from different threads, at least one of them a write, that are not ordered by happens-before. A program is correctly synchronized if none of its executions contains a data race."

14 · If count is volatile, does CountingThreads have a data race? Does it always print 2?

Esercizi 3.1.8 e 3.1.9.

Risposta modello

"No data race: by definition, accesses to volatile variables are never conflicting. But it may print 1: both threads can read 0 before either writes. Volatile gives visibility, not mutual exclusion, so the race condition remains."

Esercizio 3.1 svolto.

15 · Is a correctly synchronized program free of race conditions?

Risposta modello

"No. Correct synchronization only rules out data races. The volatile counter and addIfAbsent on a synchronized list are data race free but still have race conditions."

Lezione 4 · Classi thread-safe e sincronizzatori

16 · What is a thread-safe class in this course?

Riquadro blu: "What is the specification in this definition?"

Risposta modello

"A class is thread-safe if no concurrent execution of method calls or field accesses on objects of the class results in data races on the fields of the class. The specification is therefore absence of data races on the class state, not general correct behaviour. To show it, we cover class state, escaping, safe publication, immutability and mutual exclusion."

17 · Can list a escape in IntArrayList?

Riquadro blu, lezione 4.

Risposta modello

"Yes. get() returns a reference to the internal list. The lock only covers the return, so a thread can later call set on the list without the lock. That write and the write in the synchronized set are not ordered by happens-before: a data race on the class state. The fix is to return a copy or a single element."

Escaping.

18 · Is this program race condition free? (addIfAbsent on a synchronizedList)

Riquadro blu, lezione 4.

Risposta modello

"It is data race free, because every access goes through the synchronized methods of the list. But it is not race condition free: contains and add are separate calls, and both threads can find the element absent and add it twice. We fix it by making the compound action atomic, with synchronized (l) around it or with a synchronized addIfAbsent in the class."

Azioni composte.

19 · What is safe publication, and how do you ensure it for an int field?

Risposta modello

"State is safely published if the initial values of the fields are visible to every thread that accesses the object, which requires that initialization happens-before publication. For an int field: keep the default value if acceptable, declare it final if it never changes, volatile if it has to be volatile, or static if it belongs to the class."

Pubblicazione sicura.

20 · Why doesn't isStooge in ThreeStooges need to be synchronized?

Riquadro blu, lezione 4.

Risposta modello

"The set is final, so it is safely published; it is only modified in the constructor, so it is immutable after publication; and it never escapes, since isStooge returns a boolean. After publication there are only reads, and reads never conflict, so no data race is possible without a lock."

21 · How does a semaphore differ from a lock?

Risposta modello

"A semaphore has a capacity: up to c threads can pass acquire() at the same time, while a lock admits one. A semaphore has no owner, so any thread may call release(), and it is not reentrant. With capacity 1 it can be used as a mutex."

22 · Can you implement a bounded buffer with barriers only?

Esercizio 4.1.3.

Risposta modello

"No. A barrier blocks until a fixed number of threads arrive, independently of the buffer's content. A bounded buffer must block producers only when it is full and consumers only when it is empty, which requires counting items and spaces, and it needs mutual exclusion on the queue. Barriers provide neither."
