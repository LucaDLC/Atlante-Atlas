Come rispondere all'orale

Le domande del corso tornano sempre negli stessi 6 tipi. Per ognuno: lo schema della risposta e una frase modello in inglese, da adattare. Valgono per le risposte scritte degli assignment, per l'oral feedback e per l'esame.

Lo schema generale (senza preparazione)

Tipo 1 · "Explain why your solution is correct"

Esercizi 1.1.4, 1.1.7, 1.2.3, 1.3.2. Il testo chiede di usare "critical sections, interleavings, race conditions, mutual exclusion".

"The critical section is the read and write of count in increment(). We protect it with a ReentrantLock, calling lock() before it and unlock() in a finally block. The lock guarantees mutual exclusion: at most one thread executes the critical section at a time. Therefore no interleaving can place a read of one thread between the read and the write of the other, so no increment is lost. Each of the 20 million increments reads the value written by the previous one, and the only possible output is 20,000,000."

Tipo 2 · "Is this output possible?"

Esercizi 1.2.2, 1.2.4, il valore minimo del contatore.

  • Se sì: scrivi un interleaving concreto, azione per azione, e mostra che produce quell'output. Un esempio basta.
  • Se no: per assurdo. "Assume an interleaving produces it. Then … must happen before …, but … Contradiction." Qui un esempio non basta: devi coprire tutti gli interleaving.

"Yes. Consider the interleaving t1(1), t2(1), t1(2), t2(2): both threads read count = 0 before either writes, so both write 1 and one increment is lost. Hence the program can print 1."

Tipo 3 · "Show, using the Java memory model, that…"

Esercizi 3.1–3.3. Qui non si parla di interleaving ma di happens-before.

"t1(2) and t2(2) are conflicting actions: both write the non-volatile variable count. The only pairs relating t1 and t2 come from the thread start and termination rules, which relate them to the main thread only. Hence neither t1(2) → t2(2) nor t2(2) → t1(2) is in the happens-before order, in any execution, and the program contains a data race."

Tipo 4 · "Is this class thread-safe?"

Esercizi 4.1.2, 4.2.2. Le slide: "you must always cover these elements".

"Class state: the fields are … Escaping: all fields are private and no method returns a reference to them, so the state does not escape. Safe publication: … is final / has its default value / is volatile, so its initialization happens-before any access. Immutability: … never changes after construction. Mutual exclusion: every access to the mutable fields … holds the lock …, so all conflicting accesses are ordered by the monitor rule. Therefore there are no data races on the class state, and the class is thread-safe."

Se la classe non è thread-safe: indica l'elemento che manca e le due azioni in conflitto non ordinate. Classi thread-safe.

Tipo 5 · "Can the program loop forever?" (visibility)

Esercizi 2.2, 3.3. La risposta è quasi sempre "sì, è possibile", anche se eseguendo non lo vedi.

"Yes, it is possible. The write x = 42 in main and the reads of x in t1 are not ordered by happens-before: there is no lock, no volatile variable and no join relating them. Therefore the Java memory model does not guarantee that t1 ever sees the new value, and the loop may run forever. Declaring x volatile fixes it: by the volatile rule, the write happens-before every subsequent read."

Tipo 6 · "Is it fair? Can a thread starve?"

Esercizi 2.1.2, 2.1.4, 4.1.4.

  • Definisci: starvation = un thread che vuole entrare non ci riesce mai, mentre altri continuano a entrare.
  • Mostra lo scenario: un flusso continuo di lettori che non lascia mai il conteggio a 0.
  • Distingui: la soluzione (per esempio il flag writer che blocca nuovi lettori) dalla garanzia del lock (lock non fair: la scelta di chi entra è arbitraria). Fairness.
