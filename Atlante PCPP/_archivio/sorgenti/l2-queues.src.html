Code, Signal e Semantica Mesa

Un monitor ha due code, non una. Capire quale thread finisce dove — e cosa succede esattamente quando qualcuno chiama signal() — è ciò che rende prevedibile un monitor. E spiega perché la guardia è sempre un while.

L’interfaccia delle condition variable

await()

Rilascia il lock e blocca il thread mettendolo nella condition queue. Le due cose insieme, atomicamente.

signal()

Sveglia un thread bloccato sulla coda, se ce n’è. Quale, non è deciso.

signalAll()

Sveglia tutti i thread bloccati sulla coda, se ce ne sono.

Quando un thread si sveglia deve riacquisire il lock prima di eseguire qualunque altra cosa. Non riprende dove aveva lasciato: torna a competere.

Le due code

lock queue (o entry queue) — thread che vogliono entrare nel monitor e aspettano il lock.

condition queue — thread che sono già stati dentro, hanno trovato la guardia falsa e hanno chiamato await().

Le chiamiamo “code” per ragioni storiche, ma non si comportano come code in Java: sono più simili a insiemi. Nessuna garanzia di ordine FIFO — ed è esattamente da qui che nasce la starvation.

Mesa contro Hoare

Mesa — quella di Java

I thread svegliati da signal() tornano nella entry queue e competono di nuovo, insieme a chi era già lì.

Conseguenza: fra il momento in cui vieni svegliato e il momento in cui riesegui, un altro thread può essere entrato e aver cambiato lo stato. La condizione che ti aveva svegliato potrebbe non valere più.

Hoare

I thread in attesa su una condition variable hanno priorità su quelli nella entry queue.

Il thread svegliato riprende garantito, quindi la condizione che ha causato il signal() vale ancora. Più semplice da ragionare, più costoso da implementare.

Java è Mesa. Ogni volta che scrivi un monitor in Java devi assumere che fra signal() e la tua ripresa possa essere successo di tutto. Attiva il toggle semantica Hoare nel simulatore per vedere la differenza sulle scelte dello scheduler.

Perché while e non if

// SBAGLIATO
lock.lock();
try {
    if (writer)
        condition.await();
    readers++;   // eseguito appena svegliato
}
finally { lock.unlock(); }
// CORRETTO
lock.lock();
try {
    while (writer)
        condition.await();
    readers++;   // la guardia è stata riverificata
}
finally { lock.unlock(); }
Due motivi indipendenti, entrambi sufficienti.
1. Semantica Mesa. Vieni svegliato, torni in entry queue, ma un altro thread entra prima di te e rialza writer. Con if prosegui comunque e leggi mentre qualcuno scrive.
2. Spurious wakeup. Un thread può uscire da await() senza che nessuno abbia chiamato signal(). La JVM lo permette esplicitamente. Con if il tuo programma è rotto anche senza concorrenza avversa.
Regola pratica: await() non promette che la condizione sia vera al risveglio. Promette solo che sei tornato in esecuzione. La verifica è sempre tua — e va fatta in un ciclo.

Lock intrinseci: synchronized

In Java ogni oggetto ha un lock intrinseco con associata una condition variable. Nella Java Language Specification si chiamano monitor, ed è il nome più corretto.

Lock l = new ReentrantLock();
Condition c = l.newCondition();
l.lock();
try {
    while (property)
        c.await();
    …
    c.signalAll();
} finally {
    l.unlock();
}
Object o = new Object();

synchronized (o) {
    while (property)
        o.wait();
    …
    o.notifyAll();
}
// unlock implicito all'uscita del blocco

Corrispondenza esatta: await() → wait(), signal() → notify(), signalAll() → notifyAll(). Dentro un metodo synchronized si usa this.wait(), this.notify() e così via.

Quale lock viene usato?

La domanda che fa cadere più gente. synchronized non dice quale lock: dipende da dove lo scrivi.

Un thread svegliato torna sempre nella entry queue prima di eseguire — mai direttamente in esecuzione. È lo stesso principio della macchina a stati della Lezione 1: da blocked non si passa mai direttamente a running.
