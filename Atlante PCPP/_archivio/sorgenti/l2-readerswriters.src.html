Monitor Readers-Writers

Molti lettori insieme, un solo scrittore alla volta. Un lock semplice non basta: serve un monitor, cioè stato condiviso più metodi mutuamente esclusivi più variabili condizione. Fai girare i thread e guarda gli scrittori morire di fame.

Il problema

La regola

Una struttura dati condivisa dove i thread leggono e scrivono:

  • Molti thread possono leggere contemporaneamente, purché nessuno stia scrivendo
  • Al più uno può scrivere alla volta

Un Lock semplice risolverebbe il problema escludendo tutti — anche lettore contro lettore. Buttiamo via il parallelismo che ci interessa di più.

Il codice

public class ReadWriteMonitor {
    private int       readers   = 0;      // quanti stanno leggendo
    private boolean   writer    = false;  // c'è uno scrittore?
    private Lock      lock      = new ReentrantLock();
    private Condition condition = lock.newCondition();
}
public void readLock() {
    lock.lock();
    try {
        while (writer)
            condition.await();
        readers++;
    }
    catch (InterruptedException e) {…}
    finally { lock.unlock(); }
}

public void readUnlock() {
    lock.lock();
    try {
        readers--;
        if (readers == 0)
            condition.signalAll();
    }
    finally { lock.unlock(); }
}
public void writeLock() {
    lock.lock();
    try {
        while (readers > 0 || writer)
            condition.await();
        writer = true;
    }
    catch (InterruptedException e) {…}
    finally { lock.unlock(); }
}

public void writeUnlock() {
    lock.lock();
    try {
        writer = false;
        condition.signalAll();
    }
    finally { lock.unlock(); }
}

Tre dettagli che tornano sempre all’orale: la guardia è un while e non un if; unlock() sta nel finally; await() può lanciare InterruptedException. E nota l’asimmetria: readUnlock segnala solo se readers == 0, mentre writeUnlock segnala sempre.

Starvation degli scrittori

La versione base affama gli scrittori. I lettori entrano finché non c’è uno scrittore attivo, ma uno scrittore deve aspettare che i lettori siano zero. Se arrivano lettori in continuazione, quel momento non arriva mai.

Eseguendo ReadersWriters.java si osserva quasi sempre lo stesso schema: prima tutti i lettori, poi tutti gli scrittori.

// FairReadWriteMonitor.java
public void writeLock() {
    lock.lock();
    try {
        while (writer)
            condition.await();
        writer = true;   // prenota subito
        while (readers > 0)
            condition.await();
    }
    catch (InterruptedException e) {…}
    finally { lock.unlock(); }
}
La soluzione: lo scrittore alza writer = true prima di aspettare i lettori. Da quel momento readLock() — la cui guardia è while(writer) — blocca ogni nuovo lettore. La coda di lettori si esaurisce e lo scrittore entra. Attiva versione fair nel simulatore per vederlo.
Nel corso fairness significa assenza di starvation: se un thread è pronto a entrare nella sezione critica, deve prima o poi riuscirci. Non significa ordine FIFO — le code del monitor non sono code, si comportano più come insiemi.
