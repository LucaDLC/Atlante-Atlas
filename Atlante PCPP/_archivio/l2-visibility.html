Visibility, Reordering e volatile

Due modi diversi in cui l’hardware tradisce l’intuizione: una scrittura che non arriva mai, e due istruzioni che arrivano al contrario. Confronta le tre varianti dello stesso programma e vedi quali output sopravvivono.

Visibility · la scrittura che non arriva

// SeeNoVisibility1.java · non termina mai
boolean running = true;

Thread t1 = new Thread(() -> {
    while (running) { /* niente */ }
    System.out.println("t1 finito");
});
t1.start();
Thread.sleep(500);
running = false;
// NoVisibility1Synchronized.java · termina
boolean running = true;
Object o = new Object();

Thread t1 = new Thread(() -> {
    while (running) { synchronized(o){} }
    System.out.println("t1 finito");
});
t1.start();
Thread.sleep(500);
synchronized(o){ running = false; }

In assenza di operazioni di sincronizzazione la CPU è autorizzata a tenere running nei propri registri o nella cache bassa senza scriverlo in memoria condivisa. Quando invece si esegue unlock(), registri e cache basse vengono svuotati interamente verso i livelli di memoria condivisi da tutte le CPU.

Reordering · le istruzioni che si scambiano

Thread one = new Thread(() -> {
    a = 1;   // scritto così
    x = b;
});
Thread other = new Thread(() -> {
    b = 1;
    y = a;
});
Thread one = new Thread(() -> {
    x = b;   // eseguito così
    a = 1;
});
Thread other = new Thread(() -> {
    y = a;
    b = 1;
});

Fra a=1 e x=b non c’è nessuna dipendenza di dati e nessuna operazione di sincronizzazione. Compilatore JIT e CPU sono liberi di invertirle. Il vincolo che rispettano è preciso: il riordino non deve alterare il comportamento intra-thread — cioè il comportamento del thread eseguito da solo. Fra thread diversi, nessuna promessa.

La riga che sorprende è la seconda: synchronized elimina anche (1,1). Non perché impedisca il riordino, ma perché la mutua esclusione fa eseguire i due corpi uno dopo l’altro — e in quel caso il primo thread legge sempre lo 0 iniziale dell’altro. Con volatile i corpi restano intrecciati, quindi (1,1) sopravvive.






  
Cosa fa esattamente volatile

  

    

      

        
→
Le variabili volatile non vengono tenute nei registri della CPU né nei livelli bassi di cache nascosti alle altre CPU.

        
→
Ogni write su una volatile svuota registri e cache bassa verso la memoria condivisa.

        
→
Le variabili volatile non possono essere riordinate.

        
→
Né la read né la write sono operazioni bloccanti.

        
×
Non possono garantire mutua esclusione. È la limitazione che conta.

volatile è una forma debole di sincronizzazione: paghi meno e ottieni meno. Per counter++ non basta — servono lettura e scrittura indivisibili, e volatile non te le dà.

    

  






  Visibility e reordering esistono in tutti i linguaggi. Ogni linguaggio li affronta a modo suo: comportamento diverso delle variabili volatile, primitive di sincronizzazione diverse, strategie di compilazione diverse. Il modo formale di descrivere quali esecuzioni sono valide si chiama memory model — ed è la Lezione 3.
