Grafo Happens-Before

Il programma SeePossibleReordering può stampare (0,0), un risultato che nessun interleaving può produrre. Il motivo si legge direttamente dal grafo: clicca due azioni e scopri se sono ordinate da happens-before o se sono in data race.

Il programma, con le azioni etichettate

int x=0; // (init(x))
int y=0; // (init(y))
int a=0; // (init(a))
int b=0; // (init(b))

Thread one = new Thread(() -> {
    a=1;  // (1)
    x=b;  // (2)
});
Thread other = new Thread(() -> {
    b=1;  // (3)
    y=a;  // (4)
});

one.start();    // (start(t1))
other.start();  // (start(t2))
one.join();     // (join(t1))
other.join();   // (join(t2))
System.out.println(...); // (5)

Variable access

Read e write sulle variabili. Fanno il lavoro ma non creano nessun ordine fra thread diversi.

Synchronization action

start, join, lock/unlock, accessi volatile. Le uniche che possono generare archi fra thread.

Other

Tutto il resto. Irrilevante per il memory model.

Un'azione è la coppia t(o): chi la esegue e cosa fa. Fra t1 e t2 qui ci sono solo variable access — ecco perché il grafo li lascia scollegati.

Con volatile compaiono due archi synchronizes-with dove prima c'era il vuoto. A rigore l'arco esiste nell'esecuzione in cui la read osserva quella write — il punto è che ogni tentativo di costruire (0,0) chiude un ciclo, e un ordine parziale non può contenerne.

happens-before = chiusura transitiva di (program order ∪ synchronizes-with). Non è ordine temporale: è garanzia di visibilità. Assenza di arco non significa "andrà male", significa nessuna promessa — può funzionare per anni e rompersi su un'altra architettura.
