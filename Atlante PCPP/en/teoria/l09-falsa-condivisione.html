Week 9 · Performance

Shared updates and false sharing

A datum written by several threads passes from cache to cache at every write. Two independent data on the same cache line produce the same effect: it is false sharing.

Writing on the same datum is slow

If several threads update the same datum, the cache line makes a continuous trip from one cache to another: every write invalidates the copies of the others. The name in the slide is cache ping-pong or cache thrashing, and the cycle M → I → M → I is its symptom.

The lock is also a write to memory: if several threads take the same lock often, the state of its line keeps passing around. That is why a shared lock taken very often is slow even with the "right" lock.

When writing is fast

Two situations are fine, and they are the ones to look for:

  • immutable shared data: read by everybody, never written. They stay in S in all the caches, and reading them is fast;
  • local data: each thread writes only its own datum. It stays in M in its cache, and nobody touches it.

The lecture calls this idea "thread-local updates": a datum that changes must belong to a single thread.

False sharing: two unrelated data on the same line

The cache line is 64 bytes. Two different data, used by different threads, can be on the same line. Even if the threads do not touch each other, writing one of the two invalidates the other's copy: it is false sharing. The code does not show it: two nearby fields in an object can end up on the same line.

How it is measured

False sharing cannot be seen by reading the code: it is seen by measuring. The lecture compares versions with and without padding under the same load, and padding wins where two threads write nearby data. That is why the week's exercises ask you to measure on your own machine.

Padding is not always useful: if the threads do not write nearby data, it changes nothing. Measure first, then optimise.
