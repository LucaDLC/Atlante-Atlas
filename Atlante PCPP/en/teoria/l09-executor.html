Week 9 · Performance

Tasks, futures and the executor

For CPU-bound work the lecture uses a thread pool (the executor) that receives tasks and returns futures. The pool does not create a thread per task: it reuses a fixed number of them.

The executor: task queue and workers

A task is a piece of work to do (a Runnable or a Callable). An executor receives the tasks and runs them with a group of threads, the pool. With Executors.newWorkStealingPool() the pool has about one thread per core. Each worker has its own task queue: if its queue is empty, it steals a task from the queue of another worker (work stealing).

Future: the result that will arrive

submit returns a Future: a container for a value that will arrive later. future.get() blocks until the task is finished and returns the result. With Future<?> the task returns nothing: it serves only to wait until it finishes.

If the task throws an exception, get() rethrows it wrapped in ExecutionException. Do not ignore the result of get(), otherwise the error disappears.

Example: counting the primes in eight tasks

The count of the primes below 100 000, split into eight independent pieces. Each task counts the primes of its piece and adds them into the same shared LongAdder (without locks, see the page on striping).

Tasks or virtual threads?

The lecture compares the two paths on the same count of primes. With 1–64 threads or tasks: tasks are a bit faster than threads, while platform and virtual threads are equally fast. With 2048: tasks remain slightly faster than virtual threads, and platform threads become much slower.

workrecommended tool
waiting (I/O, network, database)virtual threads: one thread per operation
CPU computation, performance matterstasks on an executor: more control and a fixed number of threads

Do not create many platform threads. For I/O, virtual threads; for CPU-bound work, tasks. If in doubt, choose virtual threads.
