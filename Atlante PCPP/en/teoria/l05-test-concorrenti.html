Writing concurrent tests

Lecture 5 and exercises 5.1–5.2 (part of Assignment 3). A concurrent test cannot choose the interleaving: it can only make the bad one probable. Here the lecture recipe, JUnit, the barrier to start the threads together, and the real results on the sets of the exercise.

Inside, CyclicBarrier uses a lock (ReentrantLock) and a condition. When the last one arrives, it wakes everybody, but every woken thread must take that lock again before leaving await(): they leave in a queue. If every thread does one single, very short operation, the first ones have already finished when the last ones leave, and the collisions are rare.

Measured with the push test of exercise 7.2.2 (1000 threads, one push each) against a push deliberately wrong (get and then set): with CyclicBarrier the error comes out in 1 repetition out of 20. With a CountDownLatch(1) as "starting gun" (all do await(), the main does countDown() once) and join() for the end: 18 out of 20. The latch wakes the threads without making them pass through an exclusive lock. The CountDownLatch is not in the course slides: the barrier remains the "official" technique, the latch is a reinforcement.

Exercise 5.1: the sets

Three implementations of ConcurrentIntegerSet: Buggy (a HashSet without protection), Sync (to correct) and Library (ConcurrentSkipListSet). The test: 16 threads all add the same numbers 0…999, so at the end the size must be 1000; then, with the numbers already inside, they remove them all: the size must be 0.

Implementationadd: failed testsremove: failed tests
Buggy (HashSet)169 / 200 (size up to 1633)23 / 200 (size down to −219)
Sync (synchronized methods)0 / 2000 / 200
Library (ConcurrentSkipListSet)0 / 2000 / 200

Run with JDK 26 on a 12-core machine: 16 threads, CyclicBarrier, 200 repetitions (a program with the same structure as the JUnit test). A size of 1633 for a set of 1000 numbers, or a negative one, is impossible in a sequential execution.

Build the interleaving of add(5) yourself

Two threads call add(5) on an empty set. HashSet.add is not atomic: here it is split into three steps (look, insert the node, increment size). Find an interleaving that leaves 5 in the set once but with size = 2.

With add, remove and size all synchronized on the same object, the three steps of one operation can no longer be mixed with those of another (mutual exclusion), and each thread sees the writes of the previous one (happens-before of the unlock on the next lock, lecture 3). The internal set is confined: it does not leave the class (confinement).

Exercise 5.2: the semaphore

The numbers are the labels of the comments in SemaphoreImp.java: // [1] is above acquire(), // [2] above release(). So m(2) = the main calls release(), t1(1) = the thread t1 calls acquire(). The arrow → means "and then". The interleaving is written at the level of the method calls because the fields are private: from outside they cannot be touched (Hint I of the exercise).

If the semaphore were correct, the third thread would stay stopped in acquire() and would never reach the second barrier.await(). The barrier waits for 4 participants, only 3 arrive: the main stays blocked and the test does not finish. A test should be able to pass on a correct implementation. For example, in the main one can use barrier.await(1, TimeUnit.SECONDS) and handle the TimeoutException; after the timeout the counter is 2 and the assertion is true.

The bounded buffer of the lecture

Property: if producers and consumers put and take the same number of elements, the sum of the numbers put is equal to the sum of the numbers taken. Each producer accumulates its local sum and at the end adds it to a global AtomicInteger (putSum); the consumers do the same with takeSum; at the end assert(putSum.get() == takeSum.get()). The test trusts AtomicInteger: if the object used to check were wrong, the test would be worth nothing.

In HashMap size() reads a field, updated after the insertion of the node: a thread that calls size() between the insertion and the size++ of another thread sees an old value. For ConcurrentSkipListSet the documentation says that size() traverses the structure and can be inexact if the set changes during the count. Testing it is difficult: one would need to know how many elements there really are at the exact instant in which size() reads, and a test cannot stop all the threads at that point.
