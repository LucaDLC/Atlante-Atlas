Sequential consistency and linearizability

Lecture 7 (Linearizability), slides 28–45. Two ways of answering the question "is this concurrent execution correct?". The difference is one thing only: linearizability respects real time also between different threads, sequential consistency does not.

The starting point: calls that last

In a sequential program a call q.enq(x) is a single step. In a concurrent program it lasts: it starts when it is invoked (invocation) and ends when the response comes back (response). In between, other threads make other calls on the same object. To say whether the result is right one tries to put the calls in a line, one at a time, and to compare the line with the sequential specification (here: a FIFO queue).

Two calls of the same thread never overlap: a thread does one thing at a time, and the order in which it does them is the program order (the order of the code).

Sequential consistency

Definition of slide 31: a concurrent execution is sequentially consistent if there exists a sequential projection (the calls put in a line) in which:

  1. the operations happen one at a time;
  2. the program order is respected for each thread;
  3. the execution respects the specification of the object.

What is missing from the list is the important point: no rule says to respect real time between calls of different threads. If a call of B finishes before a call of A starts, in the line they can still be put in the reverse order.

Each thread is a deck, with the cards in the order of the program. Sequential consistency allows the decks to be interleaved as you like (a "riffle shuffle"), but never changing the order inside a deck. If at least one shuffle gives a line that respects FIFO, the execution is sequentially consistent.

It comes first in real time, and sequential consistency does not look at real time between different threads. deq(x) is of B, enq(x) is of A: between them there is no program order, so in the line B can be moved after A. The only forced order is the one inside A: enq(x) before enq(y).

Valid line: <q.enq(x),q.deq(x),q.enq(y)> (<q.enq(x),q.enq(y),q.deq(x)> is fine too). Empty queue, x enters, x leaves, y enters: it respects FIFO.

Yes, it is sequentially consistent. Sequential consistency only requires that the calls happen one at a time, that the program order of each thread is preserved, and that the result satisfies the FIFO specification; it does not require preserving the real-time order between calls of different threads. The only program-order constraint is that A's q.enq(x) comes before A's q.enq(y). Since q.deq(x) belongs to thread B, it can be placed after q.enq(x), giving the sequential execution <q.enq(x),q.deq(x),q.enq(y)>, which is a valid FIFO execution.

Slide 38: two objects that are individually sequentially consistent can together give an execution that is not. For this reason one cannot reason about one object at a time. Linearizability, instead, is compositional.

Linearizability

Slide 39: linearizability extends sequential consistency with one more rule:

  1. each call must take effect at an instant, at a moment between its invocation and its response.

That instant is the linearization point (the moment of the effect). By putting the calls in a line in the order of their points one obtains the linearization. Consequence: if one call finishes before another starts, even in different threads, in the line it must stand before. Real time counts.

Sequentially consistent

Program order inside each thread. Between different threads, complete freedom. Execution 7.1.1: yes.

Linearizable

Program order plus the real-time order between calls that do not overlap. Execution 7.1.2: no.

A linearization is also a valid line for sequential consistency: it respects the program order (the calls of one thread do not overlap, so their points are in order). The converse does not hold: 7.1.1 is the counterexample.

No, it is not linearizable. In a linearization each call must take effect at a point between its invocation and its response. q.deq(x) returns before q.enq(x) is invoked, so every linearization point of q.deq(x) comes before every linearization point of q.enq(x). Therefore every linearization starts with q.deq(x) on an empty queue, which cannot return x according to the FIFO specification.

Overlap: freedom, not guarantee (7.1.3 and 7.1.4)

When two calls of different threads overlap in time, their linearization points can be put in both orders. The overlap therefore gives freedom of choice. But then the chosen line must respect FIFO: if no choice respects it, the execution is not linearizable, with or without overlap.

The overlap only says which lines are allowed. To say "linearizable" one must show an allowed line that respects the specification; to say "not linearizable", show that no allowed line respects it. In 7.1.4 the allowed lines are three, and they all fail because of FIFO.

No, it is not linearizable. A's q.enq(x) and q.enq(y) do not overlap, so q.enq(x) comes before q.enq(y) in every linearization. q.deq(y) overlaps both, so its linearization point can be before, between or after them. Before: the queue is empty. Between: the queue contains only x. After: the queue is [x, y], and since x was enqueued first, a dequeue returns x. In no case can q.deq(y) return y, so no linearization satisfies the FIFO specification.
