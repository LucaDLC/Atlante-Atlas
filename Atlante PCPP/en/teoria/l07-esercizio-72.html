Exercise 7.2: Treiber stack

The lock-free Treiber stack: where the linearization points are, how push is tested, and which points the tests really reach. The point most often got wrong is 7.2.4: two tests are not enough.

The stack and its linearization points (7.2.1)

A linearization point is the instant in which a call "takes effect" for all the other threads. In the Treiber stack all the state is the reference top, so the points are the moments in which top changes, or in which it is read to decide.

7.2.4 · Do the tests cover all the points?

"Covering" a linearization point means that a test makes it run concurrently, with other threads that can collide there. A point run by one thread only tests nothing concurrent.

That is exactly why it is not everything covered. If the pushes always come before the pops, the two kinds of call never collide, and the pop never finds the stack empty while others work. The answer to 7.2.4 is no.

Pop on an almost empty stack: put m elements, then start n > m threads that do pop together. At the end: exactly m pops returned an element (with a sum equal to the one put in) and n − m returned null. So point 3 happens concurrently, while other threads still do CASes.

Optional, push and pop together: half the threads do push, half pop, all together. At the end: sum remaining in the stack + sum of the values popped = sum of the values pushed.

A simpler variant: each thread does push(x) and immediately pop(). Each thread has always made one push more than its pops, so the stack is never empty when somebody pops: at the end the sum of the popped values equals that of the pushed values, and the stack is empty. Watch out: this covers the push/pop collision, but not the pop on an empty stack.

Measured with 16 threads, barrier, 1000 repetitions. With a single push+pop per thread, a deliberately wrong push (get and then set) is never discovered, a wrong pop 1 time in 1000. With 1000 rounds of push+pop per thread: wrong push discovered 999 times out of 1000, wrong pop 1000 out of 1000; the correct stack passes 1000 out of 1000. When the text does not impose "one operation per thread", it is better to make each thread work in a loop.

No. The push test exercises the linearization point of push (the successful CAS) concurrently, and the pop test exercises the linearization point of a successful pop (the successful CAS). But the linearization point of a pop on an empty stack (the top.get() that returns null) is never reached concurrently: in the pop test there are exactly n elements for n pops, so in a correct execution no pop finds the stack empty, and in the push test the stack is emptied by a single thread. Moreover, pushes and pops never run at the same time. We therefore add a test where n threads pop concurrently from a stack with m < n elements, and check that exactly m pops return elements whose sum equals the sum pushed and n − m pops return null.
