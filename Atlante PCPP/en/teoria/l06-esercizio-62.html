Exercise 6.2: read-write lock with CAS

A lock that can be held by many readers together or by a single writer, without ever blocking: each method tries and returns at once true or false. All the state is in a single AtomicReference, changed with compareAndSet.

The idea: a single field says who holds the lock

A read-write lock distinguishes who reads from who writes: several readers together do not disturb each other (nobody changes anything), while a writer must be alone. Here the "try" version (try-lock): if the lock cannot be taken, the method does not wait, it returns false.

All the state is a single reference. That is why one CAS is enough to change it: there is never a moment in which "half" of the lock is updated.

The classes that describe who holds the lock

compareAndSet(h, new) compares references, not contents. If a thread modified the list in place (for example changing a next), the reference in holders would stay the same: the CAS of another thread would not notice the change and would overwrite it (lost update). Moreover, whoever is reading the list would see half-changed nodes. With immutable nodes every change is a new object, so a new reference, and the CAS sees it. It is the same rule as IntPair in CasNumberRange of the lecture.

6.2.1 and 6.2.2 · Writer: writerTryLock and writerUnlock

The question to ask is always: who can change the state between my read and my write?

In readerTryLock: anybody (the list is shared by many readers, and a writer can enter). The CAS is needed. In writerUnlock, after having checked that the Writer is mine: nobody, because every method called by another thread fails without touching holders (writerTryLock → false, readerTryLock → false, the two unlocks → exception). The state "Writer(me)" can be changed only by its owner. A simple set is enough; compareAndSet(h, null) would work the same and would always succeed.

set(null) also acts as a release in the sense of memory: AtomicReference.set is a volatile write, so everything the writer wrote before unlocking is visible to the next thread that reads holders and takes the lock (happens-before). That is what makes the lock useful for protecting data.

writerTryLock calls holders.compareAndSet(null, new Writer(current)). The lock is unheld exactly when holders is null, so the CAS checks that the lock is free and installs a Writer for the calling thread in one atomic step. If two writers try at the same time, only the first CAS succeeds: afterwards holders is no longer null, so the other CAS fails and returns false. It also fails if readers hold the lock (holders is a ReaderList) or if the caller already holds it, so the lock is not reentrant. There is no loop and no waiting, so the method never blocks. The Writer stores the owner thread, which writerUnlock needs.

writerUnlock reads holders once and checks that it is a Writer whose thread is the calling thread. Otherwise (null, a ReaderList, or another thread's Writer) it throws an IllegalStateException. If the check passes, it releases the lock with holders.set(null). This check-then-act is safe without a CAS because, while the calling thread holds the write lock, no other thread can change holders: writerTryLock fails because holders is not null, readerTryLock returns false when it sees a Writer, and writerUnlock and readerUnlock called by other threads throw. So the value cannot change between our get and our set. Moreover, set on an AtomicReference is a volatile write, so everything the writer did before unlocking happens-before the next thread that reads holders and acquires the lock.

6.2.3 and 6.2.4 · Readers: readerTryLock and readerUnlock

For the writer there is only one good state: null. If the CAS fails, the lock is busy: the right answer is false, at once.

For the reader the good states are many: null, [R1], [R2 → R1]… If its CAS fails because another reader has entered or left, the lock is still available to it: answering false would be wrong. So it retries.

And if in the meantime a writer has entered? The reader reads null and prepares [R]; W does CAS(null → Writer(W)) and wins; the reader's CAS (null → [R]) fails, because holders is no longer null. At the next round the reader reads the Writer and returns false. Correct: the CAS compares with exactly the state on which the reader decided.

readerTryLock is a CAS loop. It reads a snapshot h of holders; if h is a Writer it returns false. Otherwise h is null or a ReaderList, and it builds a new list with the calling thread in front of h, then tries holders.compareAndSet(h, newList). The CAS succeeds only if holders is still exactly the snapshot, so the decision was based on the current state and no concurrent update is overwritten. If it fails, another thread changed holders in the meantime. If another reader locked or unlocked, the lock may still be available, so the method retries. If a writer took the lock, the next iteration sees the Writer and returns false. Since a ReaderList is immutable, every change creates a new object, so the reference comparison in the CAS detects every change, and threads reading the old list are not affected. A CAS fails only when another thread succeeded, so the method is lock-free.

writerTryLock and writerUnlock: no loop, they always finish in a few steps (wait-free). readerTryLock and readerUnlock: CAS loop, a CAS fails only if another thread has changed the list, that is it has finished its operation (lock-free). See Wait-free, lock-free, obstruction-free.

The principle: snapshot, new copy, CAS

All the methods of the lock follow the same recipe. It works only if all the ingredients are there: a single reference, immutable objects, a CAS that checks the snapshot.

Two separate atomic fields

AtomicInteger readers + AtomicReference<Thread> writer. The reader sees writer == null; the writer sees readers == 0 and puts itself in writer; the reader does readers++. Inside both. Each operation is atomic, but the rule "readers or writer" ties two fields, and a CAS protects only one.

A single reference

Readers and writer are in the same holders. The reader and the writer do CAS on the same reference: if one changes the state, the other's CAS fails and that one checks again. It is the solution of CasNumberRange of the lecture: lower and upper inside a single immutable IntPair.

The CAS compares references. "Same reference" means "same state" only if the object cannot change. If a thread could modify the list in place, the reference would stay the same, the CAS of another thread would succeed all the same and would erase the modification. Moreover, an object with final fields published through an AtomicReference (which behaves like a volatile) is seen complete by whoever reads it.

6.2.5 · Sequential tests

One thread only, no concurrency: one checks that the rules of the lock are right. Each test creates its own lock, so the tests do not depend on each other.

6.2.6 · Parallel test: never two writers together

Many threads try to take the write lock. Whoever succeeds marks it in a shared counter "how many are inside now". If on entering it finds somebody already there, it is an overlap. At the end, when all the threads have finished, the overlaps must be 0.

6.2.7 · Challenge: no double read lock

1. The CAS succeeds only if holders is still exactly the list h on which I did contains, and that list is immutable: I checked exactly the list I replace. If in the meantime it has changed, the CAS fails and I check again.

2. Anyway only the thread itself can add or remove itself from the list (readerTryLock and readerUnlock always use Thread.currentThread()). The other threads can change the list, but not the answer to "is current there?".

With this version a test that takes two read locks from the same thread throws an exception. The right test becomes: assertTrue(lock.readerTryLock()); assertThrows(IllegalStateException.class, lock::readerTryLock);

The check contains(current) and the CAS are not one atomic step, but this is safe here. First, the CAS succeeds only if holders still refers to the same list we checked, and lists are immutable, so we check exactly the list we replace; otherwise the CAS fails and we check again. Second, only the calling thread itself can add or remove itself from the reader list, so other threads cannot change the result of contains(current).
