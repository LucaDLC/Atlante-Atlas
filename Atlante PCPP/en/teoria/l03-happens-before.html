Happens-before: the rules

Program order orders the actions inside one thread. To know whether an action of one thread surely comes before an action of another thread (and so whether the second sees the effect of the first) the happens-before rules are needed.

The pairs: what a → b means

Given two actions a, b of an execution, a happens-before b (written a → b) if the pair is obtained from one of the rules below. If a → b, the effect of a is visible to b.

The eight rules

Happens-before is not "felt": it is built, and only with these eight rules. A pair (a, b) is in the set only if a rule produces it. Three rules work inside a thread or before everything (program order, default init, final field init). Four link different threads and are the only ones that allow a thread to see the writes of another (monitor, volatile, start, termination). The last, the transitive one, glues the others into chains. If between two actions of different threads you cannot build a chain with these rules, those actions are not ordered.

The graph, rule by rule

Start rule: m(start(t1)) → t1(1), m(start(t2)) → t2(3). Termination rule: t1(2) → m(join(t1)), t2(4) → m(join(t2)). Careful: the start rule links start only to the first action of the thread, the termination rule only the last. The others follow by transitivity with the program order.

Building the sets as in the slides

At the exam the graph is written as sets of pairs: one for each rule that applies (POm, PO1, PO2 for the program order, S for start, T for termination, then possibly M for the monitor and V for volatile). The happens-before is the transitive closure of the union, indicated with ⁺: one adds all the pairs that follow from a chain. To decide whether two actions are ordered it is enough to look for a path in the graph, in one direction or the other.
