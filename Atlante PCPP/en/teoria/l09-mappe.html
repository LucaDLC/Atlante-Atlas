Concurrent maps: from one lock to ConcurrentHashMap

The second case study: eight implementations of a thread-safe hash map, from a single lock to structures without locks. The rule that runs through all of them is the same as for the counter: keep the data written close to a single thread.

The eight maps

The second case study is a thread-safe hash map. The lecture compares eight implementations, from the simplest to the Java library:

SynchronizedMapone single lock on the whole map

What the measurements show

  • The single lock (SynchronizedMap) does not scale: more threads, more time. On the server it is much worse than on the laptop.
  • With a balanced or write-dominated load, no hand-written version scales well: the library's ConcurrentHashMap wins.
  • With a read-dominated load, ConcurrentHashMap remains the best; the padding helps the versions with non-blocking reads.
  • Non-blocking reads (immutable lists) work well only if the map is read much more than it is written.

The non-blocking versions have a memory cost: every write creates a new pair, so a garbage collector and careful management are needed. That is why the lecture says the technique is not practicable in C or C++ without a GC.

The lessons

How to choose

Do not write a concurrent map from scratch: use ConcurrentHashMap. Write your own version only to understand the trade-off, or if you measure that the library is not enough for a specific case.
Striped locks and padding keep frequently written data core-local, so the cache lines can stay in the Modified state; ConcurrentHashMap combines these ideas in the library.
