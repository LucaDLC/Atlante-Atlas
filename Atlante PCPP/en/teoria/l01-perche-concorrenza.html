Why concurrency

Concurrency means doing more than one computation in the same period of time. Today almost every system uses it: websites, interfaces, operating systems, streaming, machine learning models. This page clarifies the words and the reasons, including the comparison of exercise 1.4.

The question of the ditch

Lecture 1 opens with a riddle (slide 15) that already contains the two questions of the whole course. More workers finish sooner only if the work can be divided and if they do not have to share the tools. With computers it is the same: more threads or more cores help only if the problem splits into independent parts, and the shared resources (a variable, a file, the memory) must be coordinated, at a cost.

Sequential, parallel, concurrent

Blocks of computationIs more than one core needed?
Sequentialone whole task after the otherno
Parallelthe tasks advance togetheryes
Concurrentthe computation is split into arbitrary blocks that mixno (but with more cores some blocks run in parallel)

Concurrency is an abstract concept: several flows of instructions (streams) plus a way of coordinating them. In practice you implement it with concrete tools: in Java threads, locks, monitors, semaphores; in Erlang processes and messages. The course teaches the concepts using Java.

The three reasons, according to Nygaard

The course notes use the classification of the Norwegian Kristen Nygaard.

Inherent (intrinsic)

The problem is already made of several independent flows: user interfaces, input/output. An app must read the GPS while you download a page and touch the screen.

Exploitation

The hardware can run several flows together and you want to use it: more cores, GPUs, different computers coordinated over the network.

Hidden (hidden, virtual)

Several programs share the same resources and each behaves as if it had them all to itself: the operating system that runs many programs on a few cores.

Goetz against Nygaard (exercise 1.4)

Goetz (ch. 1.1) gives three other reasons. The comparison asks for examples that fall into one classification and not the other.

GoetzIdeaClose to Nygaard…
Resource utilizationdo not leave the CPU idle while a program waits for I/Oexploitation / hidden
Fairnessseveral users or programs share the machine, each gets its parthidden
Convenienceit is more convenient to write many small programs that coordinate than one enormous oneno precise category

Look at the reason why the system is concurrent, not the system itself.

  • Only Goetz: a closed simulation, without I/O and on a single core, split into threads only because it is more convenient to write (convenience). There is no I/O (no inherent), no extra hardware is exploited (no exploitation), it shares no resources with other programs (no hidden).
  • Only Nygaard: one possible argument is a computation coordinated among many independent computers via the internet (exploitation). Goetz's three reasons are meant for programs that share one machine; coordinating different computers is not among its examples.

The text itself says that the definitions are vague and that many answers are accepted: what counts is arguing with the reason.

"A closed simulation split into threads only to structure the code is concurrent for convenience, which is one of Goetz's motivations, but it fits none of Nygaard's categories: there is no inherent I/O, no hardware being exploited and no resource sharing with other programs."
