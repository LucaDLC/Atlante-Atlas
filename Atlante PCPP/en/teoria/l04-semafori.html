Semaphores, barriers, producer-consumer

Besides locks and monitors, Java has other synchronizers. The semaphore lets in up to c threads; the barrier blocks until all have arrived. With semaphores the producer-consumer problem is solved: it is exercise 4.1.

The semaphore

Invented by Dijkstra in 1968, before monitors (1972).

A semaphore has:

  • a capacity c (in Java permits): how many threads can be in the critical section;
  • acquire(): if c > 0 it does c-- and lets through, otherwise it blocks the thread;
  • release(): if there are threads waiting it wakes one, otherwise it does c++. It never blocks.

A semaphore with capacity 1 is called a mutex: it gives mutual exclusion.

Lock

It has an owner: only whoever did lock() can do unlock(). ReentrantLock is reentrant.

Semaphore

No owner: the Java documentation says that whoever does release() need not have done acquire(). It is not reentrant: a thread that does two acquire() on a mutex blocks itself.

The documentation of Semaphore guarantees: the actions of a thread before release() happen-before the actions that follow a successful acquire() in another thread. It works like the monitor rule (unlock → lock).

Semaphores in Java

Like await(), acquire() can throw InterruptedException (checked): it must be handled with try/catch or declared with throws. The text of exercise 4.1 asks to write the concrete exception.

The barriers

A barrier has a number of parties and a method await(): if the threads waiting are fewer than parties, the caller blocks; otherwise all wake up and continue. In Java: CyclicBarrier, which resets after opening.

The semaphore counts permits: you take one (acquire, counter −1) and then give it back (release, +1). They are two different events, so two methods.

The barrier counts only arrivals. There is only one event, "I have arrived", and await() does two things together: it counts the arrival (+1) and blocks until the count reaches parties. After the barrier you hold nothing in your hand, so there is nothing to give back. Opening it is simply the last one who arrives, whoever it is; then the count returns to 0 by itself.

Yes: private CyclicBarrier barrier = new CyclicBarrier(N + 1); as a field works. JUnit 5 creates a new instance of the test class for each execution (also for each repetition of @RepeatedTest), so each repetition has its own new barrier: if one breaks (BrokenBarrierException), the next one is not affected.

It should be created inside the test method (as in CounterTest of the lecture) when the number of threads changes from one execution to the other, for example with @ParameterizedTest.

The producer-consumer problem

  • A shared data structure of fixed size.
  • The producers add elements until it is full; if it is full, they block until somebody removes an element.
  • The consumers remove elements until it is empty; if it is empty, they block until somebody adds one.
  • A good solution is deadlock free and minimises starvation.

It appears everywhere: bounded data structures, thread pools, asynchronous I/O (keyboard and mouse produce, IoT devices consume).

Exercise 4.1 · Bounded buffer with semaphores only

Constraints of the text: only Semaphore (no Lock, no synchronized), FIFO queue, state only with collections that are not thread-safe such as LinkedList or arrays.

4.1.2 · Why it is thread-safe

"The class state consists of queue, items, spaces and mutex. All fields are private and final, so they are safely published, and no method returns a reference to queue, so the state does not escape. The semaphores are thread-safe library classes. The only mutable non-thread-safe state is the content of queue, and every access to it happens between mutex.acquire() and mutex.release(). Since mutex has one permit, the accesses are mutually exclusive, and a release happens-before the next successful acquire, so all conflicting accesses to queue are ordered by happens-before."

4.1.3 · With barriers?

No. A barrier blocks until a fixed number of threads arrive, whatever the buffer contains. The buffer instead must block a producer only if full and a consumer only if empty: it needs to count places and elements, and it needs mutual exclusion on the list. The barrier offers neither.

4.1.4 · The fair flag (challenging)

  • new Semaphore(n, true): when a permit is freed it goes to the thread that has waited longest (FIFO). Without fair (default false) a thread that has just arrived can "jump the queue" (barging).
  • In the bounded buffer it does not change correctness: thread-safety, blocking on full/empty and the FIFO order of the elements hold in any case.
  • It changes starvation: with many producers, without fair one of them can in theory always lose the race for the permit. Where it matters: the limit of 5 readers of slide 57, where the course uses exactly true so that the reader who has waited longest enters first.
