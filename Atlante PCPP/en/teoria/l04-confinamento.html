Confinement and compound actions

An object that is not thread-safe can be made safe by enclosing it in a thread-safe class: instance confinement. But using only thread-safe classes is not enough to avoid race conditions: compound actions must be protected separately.

Instance confinement

Instance confinement: encapsulating access to an object that is not thread-safe inside a thread-safe class. The object is "confined": nobody reaches it except through the methods of the class.

The synchronized collections: Collections.synchronizedList(l) returns a wrapper in which every method is synchronized, and the original list is accessible only through it. Any collection can be made thread-safe this way (synchronizedSet, synchronizedMap…).

It works only if nobody keeps another reference to the inner object. If after synchronizedList(l) someone keeps using l directly, those accesses do not go through the lock.

Thread-safe classes ≠ no race conditions

Try it yourself: every call to a method of the synchronized list is an atomic step.

Repeating the experiment 200 000 times (JDK 26), [1, 1] came out 8 times. Rare, but possible: for this reason a test that "passes" proves nothing.

If "thread-safe program" means without data race (the course definition), this program is thread-safe. If it meant without race condition, it would not be. The comment in the course code says it explicitly: it depends on the definition.

Compound actions: extending a thread-safe class

A compound action is a sequence of method calls or field accesses that must happen all together in a critical section. Typical examples: check-and-set (check and then modify), iteration, navigation (for example contains followed by an action).

Solution 1: use the intrinsic lock of the collection

public void addIfAbsent(List l, Integer e) {
    synchronized (l) {
        if (!l.contains(e)) l.add(e);
    }
}

It works because the list of synchronizedList uses itself as lock: synchronized (l) takes the same lock as its methods, and nobody else can enter between contains and add. The Java documentation asks for the same thing to iterate: synchronized (list) { for (…) … }.

Same experiment with 200 000 trials and synchronized (l): [1, 1] came out 0 times.

Solution 2: a new method in the thread-safe class

Careful: on slide 79 the method is written public void synchronized. In Java it does not compile (real messages of javac):

public void synchronized addIfAbsent(T e) { if (!l.contains(e)) l.add(e); }
error: <identifier> expected
error: '(' expected
error: invalid method declaration; return type required

The modifiers (public, static, synchronized, final) go before the return type: public synchronized void addIfAbsent(…). If you write it by hand at the exam, watch the order.
