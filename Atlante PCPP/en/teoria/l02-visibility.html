Visibility, reordering, volatile

Two ways in which real execution betrays intuition: a write that another thread never sees (visibility) and instructions executed in another order (reordering). They are not "Java problems": they happen in every language with concurrency. volatile and locks are the answers.

Visibility: the write that does not arrive

Hardware intuition (slide 51): threads can run on different CPUs. Without synchronization the CPU can keep the value in its registers or in its cache, not visible to the other CPUs. Even the JIT compiler can treat the read as a constant. The slides warn that the hardware explanation is indicative: the precise rule is given by the Java Memory Model (lecture 3).

A write is guaranteed visible to a read only if the write happens-before the read. Without a lock, volatile, start/join or similar between the two, there is no guarantee.

By adding synchronized(o) around the read in t1 and the write in the main (NoVisibility1Synchronized.java) the program always terminates: the unlock of the main happens before the following lock of t1, and this order makes the write visible.

You explained with the JIT that "it caches the value and rewrites the loop". It is a possible mechanism, but at the oral it is better to give the course explanation: there is no happens-before between the write and the read, so visibility is not guaranteed; with synchronized on both methods (or with volatile) the order exists and the read sees the write. This way the answer does not depend on what a specific compiler does.

"Making both get() and set() synchronized makes them use the intrinsic lock of mi. By the monitor rule, the unlock at the end of set(42) happens-before the lock at the beginning of any subsequent get(), so that get() is guaranteed to see the value 42 and the loop in t terminates."

Reordering: the instructions that swap

// PossibleReordering.java
x = 0; y = 0; a = 0; b = 0;
Thread one   = new Thread(() -> { a = 1; x = b; });
Thread other = new Thread(() -> { b = 1; y = a; });
one.start(); other.start();
one.join();  other.join();
System.out.println("(" + x + "," + y + ")");

First try as the scheduler: which outputs do you get by mixing the steps? Then open "All possible interleavings".

With synchronized even (1,1) disappears: the two bodies run one after the other, and whoever goes first reads the initial 0 of the other. Not because the lock prevents reordering inside the thread, but because mutual exclusion prevents mixing the bodies.

volatile

volatile is a keyword for fields: volatile boolean running. It is a weak form of synchronization (slide 65): it solves the visibility and reordering problems on that variable, without blocking anyone. Precisely because it does not block, it cannot prevent two threads from mixing inside a compound operation.

  • A volatile variable is not kept hidden in the registers or caches of a CPU: the writes are made visible to the other CPUs.
  • Accesses to volatile variables are not reordered.
  • Reads and writes are not blocking.
  • It does not guarantee mutual exclusion: volatile int count; count++ remains a race condition.
