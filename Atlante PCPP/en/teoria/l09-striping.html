Week 9 · Performance

Lock striping and LongAdder

The lecture's case study: a shared counter, with nine implementations. The key step is to split a single lock into many independent locks, with padding that keeps each one on its own cache line.

One counter, one lock

The case study: a 64-bit long counter, shared by several threads, with add and longValue. The first version uses a single lock (synchronized on an object). It is correct, but all the threads compete for the same lock and its cache line: the ping-pong of the previous page.

Lock striping: one lock for each stripe

Lock striping means splitting the state into several parts (stripes), each with its own lock. Different threads usually take different locks, so they compete less. The code of the lecture uses 64 stripes.

Padding: locks and data on different lines

Even with 64 stripes, the counters and the locks are in arrays: adjacent elements in an array share a cache line. Two neighbouring stripes can therefore do false sharing. The solution of the lecture is padding: only the indices that are multiples of 16 are used (padding = 16), and the other elements stay empty. So each counter and each lock sits on a line of its own.

The results of the lecture

The lecture compares nine versions of the counter, on an Apple M3 Pro laptop and an AMD EPYC 7313 server. The conclusions, from the slide:

  • using a lock is not slow in itself, but a single lock creates contention and a lot of traffic between the caches;
  • striping improves concurrent code, but the stripes must sit on different cache lines: padding is needed;
  • the library's java.util.concurrent.atomic.LongAdder does all this correctly, and it is the choice to use;
  • the conclusions hold for five CPU architectures, from 2014 to 2023.
For a shared counter, use LongAdder. Do not write a single lock, and do not copy striping unless you have measured the need for it.
