Safe publication and immutability

Points 3, 4 and 5 of the checklist: the initial values of the fields must be visible to everybody (safe publication), what does not change must be made immutable (immutability), the rest must be protected (mutual exclusion). At the end, exercise 4.2 (Person) worked out.

Safe publication

The state of a class is published safely if, after an object has been initialised, the initial values of its fields are visible to any thread that accesses the object.

It requires that the initialisation happens-before the publication. Publishing = making the reference to the object accessible to other threads.

The course code repeats the test 10 million times, and the comment warns that on most systems the problem is not observed. The JMM however allows it: at the exam one reasons from the rules, not from what comes out when running.

If the reference to the object comes out during the constructor (for example by passing this to another thread), the problem is not safe publication, but it must always be avoided.

How to make it safe

The slides give 4 ways for primitive types and 3 for references. Each works only under certain conditions.

public class SafeInitialization {
    private int x;              // lasciato al default 0
    private final Object o;     // final
    public SafeInitialization() {
        x = 0;
        o = new Object();
    }
}

The slides warn: up to now the initialisation had been ignored "for clarity and simplicity". From this lecture on, it must be considered in the exercises.

Immutability

  • An immutable field does not change value after initialisation. Think of it as a constant.
  • final prevents reassigning the field. But a variable of object type holds a reference: final blocks the reference, not the object it points to.
  • If it never changes, data races can exist only during the initialisation.

1) the field cannot be modified after the publication; 2) it is published safely; 3) it does not escape.

Mutual exclusion

If the state is mutable, every access must be made with the same lock.

Exercise 4.2 worked out: Person

Requirements: id not modifiable; zip and address change together; all fields readable; constructor without parameters (id = previous + 1, the first is 0); constructor with the initial id (used only if it is the first person created).

"The class state is id, name, zip, address, plus the static fields nextId and firstCreated. All fields are private and the getters only return primitives or immutable Strings, so no state escapes. The static fields are only accessed inside the static synchronized method assignId, which locks on Person.class: concurrent constructor calls are ordered by the monitor rule, so each gets a distinct id. id is final, so its initialization happens-before any access after the constructor finishes: other threads can never see a partially created Person. The other fields keep their default values until set, and every access to them holds the intrinsic lock of the object, so all conflicting accesses are ordered by happens-before. Hence there are no data races on the class state."

  • 4.2.3 Run once, the program shows no errors (the version above: 400 000 distinct ids out of 400 000).
  • 4.2.4 No. One execution explores just one interleaving out of very many: a test can show the presence of an error, never its absence. Thread-safety is proved by reasoning (checklist + JMM), as in 4.2.2.

Measured on this machine, 3 threads × 30 000 persons, with the println inside the loop (one per id, name, zip, address). With synchronized removed from nextId, so with the data race inside: 0 duplicate ids in 3 executions out of 3. The test sees nothing.

The reason: System.out.println takes an internal lock on the stream. The threads spend almost all their time queued on that lock, so they execute almost one at a time and two nextId never overlap.

The same code without synchronized, but with the println outside the loop and a single check at the end (new Person().getId() must be 90 000): it comes out 52 900 – 58 300, in all 5 executions. With synchronized: 90 000, always.

To quote in 4.2.4: the same wrong code "passes" or "fails" depending on a detail that has nothing to do with concurrency. This is why a test does not prove the absence of data races.
