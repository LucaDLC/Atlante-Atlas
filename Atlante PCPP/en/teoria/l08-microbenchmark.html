Microbenchmark: from Mark0 to Mark8Setup

How to measure how long a piece of Java code takes without being fooled by the JVM. The functions Mark0…Mark8Setup of exercise 8 are a ladder: each one fixes an error of the previous one.

Where they come from: they are not standard

The Mark functions are not part of Java: they were written by Peter Sestoft, one of the two lecturers. It shows in the header of Benchmark.java (sestoft@itu.dk * 2013, 2015, 2026) and in the reading indicated in the README of week 8: his note Microbenchmarks in Java, C# and C. Mark0…Mark8 are the steps of that note. Timer.java describes itself as "crude wall clock timing utility" (a rough stopwatch).

The tool used in practice for Java microbenchmarks is JMH (Java Microbenchmark Harness, from OpenJDK). It does professionally the same things as the Mark functions: warm-up, repetitions, mean and standard deviation. The course uses the Mark functions because they are short and can be read line by line. This information about JMH comes from general knowledge, not from the course files.

Why a stopwatch is not enough

The first idea: I take the time, run the code, take the time again and subtract. With Java it gives wrong numbers for three reasons.

problemwhat happenshow to avoid it
Warm-upAt first the code is interpreted, then the JIT compiler compiles it. The first executions are much slower.repeat until the time settles
Dead codeIf the result is not used for anything, the JIT can remove the calculation and you measure nothing.use the result (dummy += …) and return it
NoiseOther processes, the garbage collector, the CPU frequency: every measurement is a bit different.repeat 10 times and give the mean ± standard deviation

A real example, measured on this PC (JDK 26.0.2.1): myPoint.hashCode() in the first round costs 490 ns (sdev 1164); after 134 million repetitions it costs 2.5 ns (sdev 0.09). The code is identical: only the JVM has compiled it in the meantime.

Mean and standard deviation

The standard deviation (sdev) says how much the measurements are spread around the mean. If it is small compared with the mean, the measurement is stable; if it is large, it is not. The line sdev = Math.sqrt((sst - mean*mean*n)/(n-1)) uses the two sums that the loop has already accumulated. An example with 4 times (the function uses 10):

name mean unit sdev count: for example Thread virt cre strt join 14557,2 ns 864,61 32768 means that creating, starting and waiting for a virtual thread costs on average 14 557 ns, with sdev 865 ns (6% of the mean), measured over a round of 32 768 calls. An sdev close to or above the mean means the number is not reliable.

Timer and Mark8Setup: measuring without the setup

What exercises 8.1–8.4 measure

The thread of the assignment: how much a thing really costs when in Java it seems free (a library function, a thread, a keyword)? Each exercise measures a different cost with the same Mark functions. The numbers are from this PC (i5-11400H, JDK 26.0.2.1).

The cost is never "zero" and never "what it seems": a library call, a thread or a keyword can cost from a few ns to hundreds of µs. To decide (thread or not? volatile or not?) one must measure rigorously: warm-up, used result, repetitions, sdev. And that is why the Mark functions exist.

Practical rules

Never inside an IDE or in debug mode (the text of the exercise says so). Close the other applications; on a laptop connect the power. Always do at least two runs and look at the sdev: a much higher sdev in one run (as with tan at ±5.4 ns in one run out of two) indicates noise, not a property of the function. The value returned by f must depend on the measured work, otherwise the JIT eliminates it.

From the project folder: gradle -q -PmainClass=exercises08.Benchmark run (change the class for the others: TestTimeThreads, TestTimeSort, TestTimeVolatile). -q prints only the output of the program; to save it add > file.txt. Without Gradle: from the folder app/src/main/java, javac exercises08/*.java and then java exercises08.Benchmark.
