Exercise 6.1: CasHistogram

A lock-free histogram made of AtomicInteger, using only get and compareAndSet, and a test that compares it with the sequential version. First what a histogram is, then the class, then the test.

What a histogram is

A row of bins, each with a counter: it serves to count how many times each thing happens. The interface Histogram:

methodwhat it does
increment(7)+1 to bin 7
getCount(7)the value of bin 7
getSpan()how many bins there are (in exercise 30)
getAndClear(7)returns the value of bin 7 and sets it back to 0

Histogram1

int[] and counts[bin] = counts[bin] + 1: read, then write. Perfect with one thread; with several threads it loses increments (race condition). In the test it serves as the reference, used by one thread only.

CasHistogram

The same thing, but each bin is an AtomicInteger and the increment is a CAS loop: it loses nothing even with many threads. It is the class under test.

6.1.1 · The class

The rule of final fields does not apply only to the reference counts: a thread that sees the object after the constructor also sees everything that can be reached from that field as it was at the end of the constructor. So it sees the array and the 30 AtomicIntegers already created, each at 0. Later changes are visible because each AtomicInteger behaves like a volatile.

Immutable variables: the reference counts (final, never reassigned) and, in fact, the contents of the array: after the constructor counts[i] always points to the same AtomicInteger. Only the values inside the AtomicIntegers are mutable: they are the state of the histogram.

i) No escaping: the state is the array counts and the AtomicInteger objects in it. The field is private, no method returns the array or one of its AtomicIntegers (they only return int values), and the constructor neither starts threads nor passes this to other objects. ii) Safe publication: counts is final, so any thread that obtains a reference to the object after construction sees the array and all AtomicIntegers initialised to 0. Later updates are visible because each AtomicInteger behaves like a volatile variable. Immutable: the reference counts and, in practice, the array contents (each slot always points to the same AtomicInteger). Only the values inside the AtomicIntegers change.

With AtomicIntegerArray and incrementAndGet / getAndSet the class is thread-safe, but it violates the text: AtomicInteger is required, and only get and compareAndSet may be used.

6.1.2 · Is getAndClear atomic?

The method does two things: get (reads the value) and clear (sets it back to 0). The question: can another thread slip in between the two and make something be lost? With the CAS loop, no.

get, then set(0)

v = c.get(); c.set(0); return v; If T2 increments between the two lines, set(0) erases its increment and nobody returns it: lost.

get, then CAS(v, 0)

The CAS zeroes only if the value is still v. Otherwise it tries again. Nothing is lost: it behaves as if get and clear were one atomic operation.

Yes. getAndClear reads the value and then calls compareAndSet(oldValue, 0), which writes 0 only if the bin still contains oldValue. If another thread changes the bin between the read and the CAS, the CAS fails and the loop retries. So when the CAS succeeds, the returned value is exactly the value that was replaced by 0, and no update can happen in between and be lost: the get and the clear take effect together at the successful CAS.

6.1.3 · What the test does

countFactors(p) says into how many primes p decomposes, and it is the bin to increment. With the numbers from 0 to 9:

numbersdecompositionbin
0, 1none0
2, 3, 5, 7are primes1
4, 6, 92·2, 2·3, 3·32
82·2·23

Resulting histogram: bin 0 → 2, bin 1 → 4, bin 2 → 3, bin 3 → 1. The test does the same with the numbers from 0 to 4999.

Tried by putting Histogram1 (not thread-safe) in the parallel part: it passed 100 repetitions out of 100. Each thread does a single increment, and the barrier wakes the 5000 threads almost one at a time, so they rarely collide. It is the test the exercise asks for, but it is a good example of "a test that passes proves nothing". Each repetition lasts about a second (creating 5000 threads costs): 20 repetitions are enough.

The test goes in app/src/test/java/exercises06/TestHistograms.java, with package exercises06;. In src/main JUnit is not available (it is a testImplementation dependency), and without the package Histogram1, which is not public, cannot be seen.
