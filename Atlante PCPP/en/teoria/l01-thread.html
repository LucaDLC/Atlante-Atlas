Threads, states, scheduler

A thread is not always executing: it passes between some states, and who decides when is the scheduler, in a non-deterministic way. From this freedom come the interleavings, and so all the problems of the course.

The Tivoli turnstile

A thread is a flow of instructions that advances on its own: "an independent sequence of program statements". Every Java program starts with one thread, main; others are created with new Thread(…) and start with start(). All the threads of a program see the same fields of the objects: that is shared memory, the way they communicate, and the source of the problems of the course. join() makes a thread wait until another has finished.

The example of the lecture: a thread simulates 10 000 people who enter through a turnstile and increment a shared counter.

The states of a thread

Slide 43 uses a simplified model with three states. The state machine below follows the life of a thread.

TransitionWho causes it
startthe program, by calling start()
schedule / suspendthe system scheduler: not controllable, not predictable
waitthe thread itself, with a blocking call
eventother entities: other threads, exceptions, hardware interrupts

From blocked you never go directly back to running: you always pass through enabled. You will find the same idea in monitors: a thread woken by signal() must compete again for the lock.

Non-determinism

Two threads t1 and t2, both enabled. The scheduler can produce, for example:

1. t1(running) → t1(enabled) → t1(running) → t1(enabled) → …
2. t2(running) → t2(enabled) → t2(running) → t2(enabled) → …
3. t1(running) → t1(enabled) → t2(running) → t2(enabled) → …
4. … infinite esecuzioni diverse

No assumption is allowed about which thread runs next. This is why a test that passes does not prove that a concurrent program is correct: you have seen one execution out of infinitely many. Correctness is argued from the constraints (mutual exclusion, happens-before), not from the executions observed.
