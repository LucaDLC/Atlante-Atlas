Wait-free, lock-free, obstruction-free

Lecture 6 (Lock-Free Data Structures), slides 14–17. Without locks no thread stays blocked by another, but "who finishes, and when?" has three different answers: they are the three progress conditions of non-blocking data structures. Herlihy, section 3.8.

Where we start: the problem of locks

With a lock, if the thread that holds it is suspended by the scheduler (or blocks), all the others wait, for a time that does not depend on them. A non-blocking implementation avoids locks and uses the CAS: no thread can hold the others still.

The three conditions say how strong the guarantee that the calls finish is. They are all read with the same question: "for whom is it guaranteed that it finishes in a finite number of steps?"

No: they are two different questions.

  • Is the result right? (safety: no lost increments, no duplicates). It is guaranteed by the CAS: it writes only if the value is still the one read, otherwise it writes nothing.
  • Do the calls finish? Can somebody stay blocked? (progress, that is liveness). This is what wait-free, lock-free and obstruction-free measure.

Even a lock gives a right result. What the lock does not guarantee is progress: if the thread holding it stops, everybody stops.

The three definitions

conditionguarantee (slides)in wordswho finishes
wait-freeevery call finishes in a finite number of steps"my operations finish, whatever the others do"everybody
lock-freerunning the method guarantees that some call (even a concurrent one) finishes in a finite number of steps"the operations of somebody finish"at least one
obstruction-freefrom any point where it runs alone (in isolation), it finishes in a finite number of steps"my operations finish, if they let me run"whoever stays alone

wait-free ⇒ lock-free ⇒ obstruction-free. Each condition implies the one below:

  • if everybody finishes, then somebody finishes: wait-free ⇒ lock-free;
  • if somebody always finishes, and I am running alone, that somebody can only be me: lock-free ⇒ obstruction-free.

The converse does not hold: the guarantee weakens going down.

Lock-free: the CAS loop

Slide 17 asks: what condition does addAndGet of AtomicInteger have, written with a CAS loop?

do {
    oldValue = get();
    newValue = oldValue + delta;
} while (!compareAndSet(oldValue, newValue));

Most non-blocking structures are lock-free: the Treiber stack, the Michael-Scott queue, ConcurrentSkipListSet, the CasHistogram of exercise 6.1 (increment, getAndClear).

Wait-free and obstruction-free: examples

Wait-free

No loop that depends on the others. getCount(bin) of CasHistogram does a single get(): it finishes in one step, whatever happens. Also getSpan().

Obstruction-free

Two threads can cancel each other out for ever: each undoes the other's half-done work, and nobody finishes (livelock). Like two people in a corridor who always move to the same side. But if one of the two stays alone, it finishes.

Without locks, who guarantees that the CAS is atomic?

Neither lock nor trust: the guarantee comes from the processor. The CAS is a single machine instruction (slide 8: modern processors have dedicated instructions, such as compare-and-swap). The comparison and the write happen inside that one instruction, and the hardware prevents another core from touching that memory cell until the instruction is finished (on x86 it is LOCK CMPXCHG).

So there is a "block", but it lasts one instruction, a few nanoseconds, and the hardware manages it. No thread can hold it and then fall asleep: the difference with a lock(), which stays taken for the whole critical section, even while the thread is suspended.

Lock: pessimistic

"Somebody might disturb me, so first I book and close the door, then I work." The others wait outside, even if they would not have touched anything.

CAS: optimistic (slide 17)

"Probably nobody disturbs me: I work on my copy and at the end I check. If somebody has changed the value, I throw my work away and redo it." It is optimistic concurrency.

The CAS loop works like a git push. You work locally (you read the value, compute the new one). Then you push: if in the meantime nobody has pushed, it goes through. If somebody has pushed before, the push is rejected (it does not overwrite the work of others): you pull, redo the computation on the new value, push again. Nobody has ever locked the repository.

The CAS is indivisible, and no thread can hold the others hostage. But the code around it can still be wrong:

  • one CAS per field when the invariant ties several fields: NumberRange below ends with lower > upper;
  • writing with set() instead of the CAS: "read, compute, set" is again a non-atomic read-modify-write, and updates get lost;
  • using a value different from the one of the CAS: in getAndClear one must return the value that the CAS zeroed, not a re-read done afterwards;
  • the value comes back the same: the CAS compares only the value, so A → B → A looks "unchanged" (the ABA problem, later in the lecture).

Does the CAS replace locks?

No, on both counts. In a lock-free structure there are no locks: CasHistogram, the Treiber stack and ConcurrentSkipListSet are correct without any lock(). The CAS does both jobs by itself: it makes the update atomic (safety) and blocks nobody (progress).

And it is not certain that it is faster: with many threads competing for the same value the CASes often fail and one retries for nothing. Slides 32–33 (random number generator) show that, under high contention, the CAS version can scale worse, and that locality matters more (each thread with its own object, ThreadLocal) than being lock-free. The real advantage of the CAS is the progress guarantee, not the speed.

The limit of the CAS: it acts on one variable at a time. If the invariant ties several fields, two separate CASes are not enough.

Practical rule: state in one variable (or packable into an immutable object) → the CAS is enough and replaces the lock. State spread over several objects, or one needs to wait for a condition (buffer not empty) → locks and monitors remain the right tool.

Non-blocking does not mean busy-wait

The busy-wait (while (i > 0) { }) waits for another thread to change something: if that thread stops, the loop runs for ever. In the course it is forbidden: solutions with busy-wait are rejected.

A CAS loop instead does not wait for anybody: it repeats because another thread has gone ahead, and with the three conditions termination is guaranteed (at least in isolation). That is why the CAS loop is allowed, but only for implementations based on CAS.

"The CAS loop in addAndGet is lock-free but not wait-free: a CAS fails only if another thread's CAS succeeded, so some call always completes, but a single thread may keep losing and never finish. Wait-free implies lock-free, which implies obstruction-free."
