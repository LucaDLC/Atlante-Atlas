synchronized: intrinsic locks

In Java every object already contains a lock with a condition variable: the intrinsic lock (the Java specifications call it a monitor). It is used with the keyword synchronized. The delicate point is to understand which object acts as the lock.

synchronized block = lock + try/finally

In Java every object already contains a lock, called the intrinsic lock (or monitor lock). The keyword synchronized uses it without having to create a ReentrantLock: it takes the lock on entering a block or a method and releases it on exiting. It does the same as the lock + try/finally idiom, with fewer lines and without the possibility of forgetting the unlock.

With a Lock

Lock l = new ReentrantLock();
l.lock();
try {
    // sezione critica
} finally {
    l.unlock();
}

With the intrinsic lock

Object o = new Object();
synchronized (o) {
    // sezione critica
}

The lock of o is taken on entering the block and released on exiting, even with an exception. And it is reentrant.

On a method: which lock?

synchronized can also be written in front of a method. Then the important question is: which object provides the lock? It depends on whether the method is instance or static, and getting this answer wrong is the mistake of exercise 2.3.

Exercise 2.3: the class Mystery

class Mystery {
    private static double sum = 0;
    public static synchronized void addStatic(double x) { sum += x; }
    public synchronized void addInstance(double x)      { sum += x; }
    public static synchronized double sum()             { return sum; }
}

Everything is private and all the methods are synchronized: it looks safe. It is not.

In this program no: main calls sum() after t1.join() and t2.join(). The last writes of the threads come before the join by the termination rule (lecture 3), so the read sees the final values without data race. In a class used by threads that read while others write, instead, it would be needed.

"A synchronized instance method locks this, the Mystery object, while a static synchronized method locks Mystery.class. Since t1 and t2 hold different locks, their executions of sum += x are not mutually exclusive, and the non-atomic read-modify-write on the static field sum can interleave and lose updates."
