Actions and executions

Visibility and reordering make the real behaviour hard to predict by looking at the hardware. The Java Memory Model (JMM) gives rules at the level of the language to say which executions are valid. One starts from three words: action, execution, program order.

Why a memory model is needed

  • Hardware changes from one computer to another: different instructions, different memory management.
  • Compilers, runtimes and CPUs make optimisations (reordering, rewriting of the code) that produce "paradoxical" results: the loop that does not end, the output (0,0).
  • The JMM is a set of rules: the JVM generates only executions valid under those rules, on any hardware. So the programmer can predict what happens.

The "normal" behaviour you expect. A concurrent execution is sequentially consistent if 1) it respects the order of the instructions inside each thread and 2) the operations seem to happen in an instant, one at a time. The output (0,0) of PossibleReordering is not sequentially consistent.

Guaranteeing it for every program would cost all the optimisations. The JMM guarantees it only for correctly synchronized programs (data race page).

Actions: "who does what"

An action is a pair t(o): t is the thread, o the operation. For example t1(1) = the thread t1 executes the operation numbered (1).

TypeExamples
Variable accessreading or writing a variable of the program: a=1 (writing a), x=b (reading b and writing x)
Synchronizationsynchronization primitives: lock(), unlock(), start(), join()…
Othereverything else (creating an object, printing…)

Executions

An execution is a sequence of actions σ = α1, α2, α3, …

Program order

Given two actions a, b of the same thread, a comes before b in the program order if, executing that thread alone, a would be executed before b. It is defined on the code: the reorderings of the compiler or CPU do not count.

For each thread it is a total order: taking any pair of its actions, one of the two comes first.
