Exercise 3.1 worked out

CountingThreads: two threads increment count once. It is the exercise that trains the whole Java Memory Model. Here it is worked out one point at a time, following the 6-step strategy; at the end 3.2 and 3.3 in brief.

The program with the numbered operations

// main (thread m)
count = 0;                              // (init)
CountingThread t1 = new CountingThread();   // (new1)
CountingThread t2 = new CountingThread();   // (new2)
t1.start();                             // (start(t1))
t2.start();                             // (start(t2))
t1.join();                              // (join(t1))
t2.join();                              // (join(t2))
System.out.println("count=" + count);   // (p)

// run() di CountingThread (t1 e t2)
int temp = count;      // (1)
count = temp + 1;      // (2)

In your answers use the numbering you want, but declare it. Here t1(1) is the read of t1, t2(2) the write of t2.

3.1.1 · The actions

ActionType
m(init)variable access (write of count)
m(new1), m(new2)other (creation of the thread objects)
m(start(t1)), m(start(t2)), m(join(t1)), m(join(t2))synchronization
m(p)variable access (read of count)
t1(1), t2(1)variable access (read of count)
t1(2), t2(2)variable access (write of count)

new1/new2 also write the local variables t1 and t2 of the main: classifying them as variable access is acceptable, as long as you say so. They are not shared, so they do not change the analysis.

3.1.2 – 3.1.4 · The sets of pairs

You wrote the order as a chain of arrows (m(5) → m(6) → …). A synchronization order is a sequence (a total order), not a set of happens-before pairs: write it in brackets with commas, as in slide 21.

3.1.5 · Proving the data race

You wrote "there may be a race condition between…". Here the right word is data race between conflicting actions: race condition is something else (lock page). And "count == 1" does not prove the data race: the proof is to show that neither of the two arrows is in the HB, that is, that from the sets PO, S, T no path leaves between the actions of t1 and those of t2.

3.1.6 – 3.1.7 · With a lock

// run()
l.lock();              // (0)
int temp = count;      // (1)
count = temp + 1;      // (2)
l.unlock();            // (3)   (con try/finally)

In 3.1.6 you wrote the two complete chains t1 → t2 and t2 → t1 and spoke of "two different interleavings". The question asks whether more happens-before sets arise: the answer is "yes, two", HB1 and HB2, each with one extra pair given by the monitor rule (unlock of one → lock of the other).

In 3.1.7 you listed pairs inside the same thread (program order). Those were already there: the proof must take the conflicting pairs between t1 and t2 and show the path that orders them, in HB1 and in HB2, as in the two steps above.

3.1.8 – 3.1.9 · With volatile count

You answered No and wrote that the reads and writes of a volatile variable are "synchronization actions". Both things must be corrected: they are variable access, and the definition of conflicting actions excludes volatile variables. So no data race. The count == 1 that you described is true, but it is a race condition: it is exactly the point of 3.1.9.

"Yes, all executions are data race free. By definition in the Java memory model, accesses to volatile variables are never conflicting actions, and the only shared variable, count, is volatile. Therefore there is no pair of conflicting actions and hence no data race. This does not prevent the race condition: both threads may read 0 before either writes, so the program may still print count=1."

3.1.10 – 3.1.11 · Mutual exclusion with happens-before (challenging)

3.1.10 Mutual exclusion for this program: in every execution t1(3) → t2(0) or t2(3) → t1(0) holds. That is: the critical section of one thread ends (unlock) before the other enters (lock).

3.1.11 With the body in a while(true): each iteration i of t1 has actions t1(0i) … t1(3i). For any iteration i of t1 and j of t2, the synchronization order puts one of the two locks before the other unlock; the monitor rule gives t1(3i) → t2(0j) or t2(3j) → t1(0i), and with the program order all the conflicting pairs of the two iterations come out ordered. Since it holds for every pair of iterations, no execution (even an infinite one) has a data race.

3.2 · StringSet in brief

public synchronized int findOrAdd(String s) {   // lock(s) · (a) indexOf · (b) add · unlock(s)
    int ret = list.indexOf(s);
    if (ret == -1) list.add(s);
    return ret;
}
public int find(String s) { return list.indexOf(s); }   // (c) indexOf, SENZA lock
  • 3.2.1 In conflict: t1(b) (add = write) and t2(c) (indexOf = read). t2 makes no synchronization actions on the monitor of s: the only pairs that link t1 and t2 go through the main (start), and give only m(start(t1)) → … and m(start(t2)) → t2(c). No order between t1(b) and t2(c): data race, the program is not correctly synchronized.
  • 3.2.2 With find synchronized, t2 does lock/unlock on the same monitor. Two cases: t1(unlock) → t2(lock) or t2(unlock) → t1(lock) (monitor rule), so t1(b) and t2(c) are always ordered: correctly synchronized. find can return 0 or -1 depending on who enters first: it is a race condition, not a data race.
  • 3.2.3 The data race of 3.2.1 is present in all the executions: the list starts empty, so add is always executed, and no synchronization order introduces pairs between t1 and t2.

3.3 · The loop that may not end, in brief

int x = 0;
Thread t1 = new Thread(() -> {
    while (x == 0) { }                 // (r) lettura di x, ripetuta
    System.out.println("t1: x=" + x);
});
t1.start();                            // (start(t1))
x = 42;                                // (w) scrittura
System.out.println("Main: x=" + x);
  • 3.3.1 To prevent infinite executions m(w) → t1(r) must hold for a read of t1 that comes after the write: the write x = 42 must happen-before a read of the while, so that this read sees 42 and exits.
  • 3.3.2 It does not hold: the only rule linking m and t1 is the start rule, m(start(t1)) → t1(r1). But m(w) comes after m(start(t1)) in the program order of the main, and there is no lock, volatile or join linking m(w) to the reads of t1. No execution has m(w) → t1(r).
  • 3.3.3 Declare volatile int x. m(w) is a write to a volatile variable; each read t1(r) of the while that in the execution comes after m(w) is a "subsequent read": by the volatile rule m(w) → t1(r). That read sees 42 and the loop ends. Alternatively: read and write inside synchronized on the same object (monitor rule).

The question asks which pair must be ordered, not the whole happens-before of the program: it is enough to say "the write x=42 of the main must happen-before a read of x in the while of t1", and explain why with that pair the loop ends.
