Thread-safe classes

Analysing a whole concurrent program with the JMM becomes impossible beyond a few lines. One analyses one class at a time. This page gives the course definition of thread-safe class and the first two points of the checklist: class state and escaping.

Correctness and specification

  • A program is correct if it respects its specification.
  • The specification is a precise sentence about the wanted behaviour. Examples: "several readers together, a single writer and only with no readers"; "the output must be PEOPLE*num_threads".
  • In the course specifications remain sentences (no formal logic).

Reasoning about thousands of lines (servers, operating systems, GUIs) is unmanageable. In an object-oriented language one analyses the class: only the method calls and the field accesses done concurrently remain.

The definition of the course

"A class is thread-safe if no concurrent execution of method calls or field accesses (read/write) on objects of this class results in data races on the fields of the class."

In plain words: however the methods (or the reads/writes of the fields) of an object of this class are called in parallel, there is never a data race on the fields of the class.

In the course "thread-safe" does not mean "seems to work when concurrent". It only means: no data race on the fields. The specification of this definition is therefore "absence of data races". It is inspired by the definition of the JMM: "a program is correctly synchronized iff none of its executions contains data races".

It differs from Goetz ch. 4, which speaks of class invariants; it resembles Goetz ch. 2, p. 18.

"A concurrent program is thread-safe if and only if it is data race free." Do not confuse: a thread-safe class concerns its fields, a thread-safe program concerns all its shared variables. Goetz does not define thread-safe programs.

What it guarantees

No data race on the fields of the class, for any concurrent use of its methods.

What it does not guarantee

No race condition. A program that uses only thread-safe classes can still get a wrong result: example in confinement and compound actions.

The checklist: 5 elements

To show that a class is thread-safe one must show that, in any concurrent execution of accesses to the fields and method calls with at least one write, the actions are ordered by happens-before. In practice these elements are always checked.

"When asked to reason about the thread-safety of a class, you must always cover these elements." An answer that only says "the methods are synchronized" is incomplete. The slides quote a theorem (optional readings): these elements together are enough to guarantee thread-safety.

1 · Class state

The state of a class is its fields. They are the shared variables to protect when the class is used by several threads.

The definition speaks only of the fields of the class. An object that comes from outside as a parameter is not state of the class.

Better avoid methods that take objects as parameters and modify them: the class cannot guarantee happens-before on the actions on that object, because other threads use it as they like.

2 · Escaping

The state does not escape (does not escape) if it can be reached only through the public methods of the class. If it escapes, a thread can use it without the intended synchronization, and happens-before can no longer be guaranteed.

First way of escaping: a field that is not private

Declaring private all the fields of primitive type ensures that they are touched only by the methods of the class.

Second way: returning a reference to the state

private is not enough if a method returns the object that is part of the state.

Do not write methods that return references to objects of the state. Return values (an int, an immutable element such as Integer or String) or a copy.

"The class state is the field a. It escapes through get(), which returns a reference to the internal list: a thread can then call set on it without holding the lock, so that write and the write in set(…) are not ordered by happens-before. This is a data race on the class state, hence the class is not thread-safe."

HashSet.add does "look whether it is there → write the node → size++" in three separate steps: two threads can both look before one writes.

ConcurrentSkipListSet (on top of ConcurrentSkipListMap) does the decisive step with a compare-and-set (CAS): "write the new node only if the pointer still has the value I read". It is a single atomic operation of the hardware: if another thread has changed something in the meantime, the CAS fails and the thread restarts the search, and this time it finds the key already present → add returns false. For remove it is the same: the node is deleted with a CAS on the value (from v to null), and only one thread wins.

The counter is updated (addCount(±1), a thread-safe LongAdder) only by the thread that won the CAS: no duplicates, no double decrements. Verified on the source of JDK 26.
