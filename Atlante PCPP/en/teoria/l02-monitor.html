Monitor and condition variable

A simple lock says "one at a time". But some problems want richer rules: many readers together, or a single writer. For this one needs a monitor: shared state, methods in mutual exclusion and wait queues for those who must wait.

The readers and writers problem

  • A shared data structure, on which threads read or write.
  • Many threads can read at the same time, as long as nobody is writing.
  • At most one can write, and only if nobody is reading.

A lock would guarantee safety, but it would also exclude reader against reader: you would throw away exactly the parallelism that the problem allows. What is needed is something that decides who can enter based on the state.

What a monitor is

A monitor is a shared state plus significant operations on that state, which protect it from corruption even when executed concurrently.

The three operations of a condition variable

await()

Releases the lock and blocks the thread in the queue of the condition. Both things together.

signal()

Wakes one thread in the queue, if there is one. Which one is not decided.

signalAll()

Wakes all the threads in the queue.

A woken thread must take the lock again before doing anything else. Do not confuse the condition variable with the conditions of the if and the while: it is a queue.

ReadWriteMonitor, method by method

The monitor of the lecture for the readers-writers problem. The state is two private fields: readers (how many readers are inside) and writer (is there a writer?). The four methods take the lock, check the state in a while, wait with await() as long as needed, update the state and release the lock. Whoever frees the resource wakes the others with signalAll().

Why while and not if

For correctness no: whoever wakes checks its condition again in the while and, if it cannot enter, goes back to waiting. The check only avoids useless wakeups: if there are still readers, no writer could enter anyway.

Exercise 2.1: the same monitor with synchronized

Every Java object already has a lock and a condition variable inside. With synchronized one uses wait(), notify(), notifyAll() instead of await(), signal(), signalAll().

One: the intrinsic one of the object on which you do synchronized. Readers and writers all wait in the same queue, with wait(), and are woken with notifyAll(). With ReentrantLock instead you can create several conditions (lock.newCondition() twice), for example one for the readers and one for the writers (exercise 2.1.5).

Checked: 15 readers and 5 writers, 200 accesses each, no violation of the specification.
