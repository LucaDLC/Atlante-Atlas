synchronized: indre låse

I Java har hvert objekt allerede en lås med en condition variable indeni: den indre lås (Java-specifikationerne kalder den en monitor). Den bruges med nøgleordet synchronized. Det vigtige punkt er at forstå, hvilket objekt der fungerer som lås.

synchronized-blok = lås + try/finally

I Java har hvert objekt allerede en lås, kaldet den indre lås (eller monitor-låsen). Nøgleordet synchronized bruger den uden at skulle oprette en ReentrantLock: den tager låsen, når man går ind i en blok eller en metode, og frigiver den, når man går ud. Det gør det samme som idiomet lås + try/finally, med færre linjer og uden risiko for at glemme unlock.

Med en Lock

Lock l = new ReentrantLock();
l.lock();
try {
    // sezione critica
} finally {
    l.unlock();
}

Med den indre lås

Object o = new Object();
synchronized (o) {
    // sezione critica
}

Låsen på o tages, når man går ind i blokken, og frigives, når man går ud, også ved en undtagelse. Og den er reentrant.

På en metode: hvilken lås?

synchronized kan også skrives foran en metode. Så er det vigtige spørgsmål: hvilket objekt giver låsen? Det afhænger af, om metoden er instans- eller static, og at give det forkerte svar er fejlen i øvelse 2.3.

Øvelse 2.3: klassen Mystery

class Mystery {
    private static double sum = 0;
    public static synchronized void addStatic(double x) { sum += x; }
    public synchronized void addInstance(double x)      { sum += x; }
    public static synchronized double sum()             { return sum; }
}

Alt er private, og alle metoderne er synchronized: det ser sikkert ud. Det er det ikke.

I dette program nej: main kalder sum() efter t1.join() og t2.join(). Trådenes sidste skrivninger kommer før join ifølge afslutningsreglen (forelæsning 3), så læsningen ser de endelige værdier uden data race. I en klasse, der bruges af tråde, der læser mens andre skriver, ville den derimod være nødvendig.

"A synchronized instance method locks this, the Mystery object, while a static synchronized method locks Mystery.class. Since t1 and t2 hold different locks, their executions of sum += x are not mutually exclusive, and the non-atomic read-modify-write on the static field sum can interleave and lose updates."
