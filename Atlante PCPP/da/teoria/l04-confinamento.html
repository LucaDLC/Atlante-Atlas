Indkapsling og sammensatte handlinger

Et objekt, der ikke er thread-safe, kan gøres sikkert ved at lukke det inde i en thread-safe klasse: instance confinement. Men at bruge kun thread-safe klasser er ikke nok til at undgå race conditions: sammensatte handlinger skal beskyttes særskilt.

Instance confinement

Instance confinement: at indkapsle adgangen til et objekt, der ikke er thread-safe, i en thread-safe klasse. Objektet er "indesluttet": ingen når det andet end gennem klassens metoder.

De synchronized collections: Collections.synchronizedList(l) returnerer en indpakning, hvor hver metode er synkroniseret, og den oprindelige liste er kun tilgængelig gennem den. Enhver samling kan gøres thread-safe på denne måde (synchronizedSet, synchronizedMap…).

Det virker kun, hvis ingen holder en anden reference til det indre objekt. Hvis nogen efter synchronizedList(l) bliver ved med at bruge l direkte, går disse adgange ikke gennem låsen.

Thread-safe klasser ≠ ingen race conditions

Prøv selv: hvert kald til en metode på den synkroniserede liste er et atomart trin.

Ved at gentage eksperimentet 200 000 gange (JDK 26) kom [1, 1] 8 gange. Sjældent, men muligt: derfor beviser en test, der "går igennem", ikke noget.

Hvis "thread-safe program" betyder uden data race (kursets definition), er dette program thread-safe. Hvis det betød uden race condition, ville det ikke være det. Kommentaren i kursets kode siger det udtrykkeligt: det afhænger af definitionen.

Sammensatte handlinger: udvidelse af en thread-safe klasse

En sammensat handling er en følge af metodekald eller feltadgange, der skal ske helt i en kritisk sektion. Typiske eksempler: check-and-set (kontrollér og derefter ændr), iteration, navigation (for eksempel contains efterfulgt af en handling).

Løsning 1: brug samlingens indre lås

public void addIfAbsent(List l, Integer e) {
    synchronized (l) {
        if (!l.contains(e)) l.add(e);
    }
}

Det virker, fordi listen i synchronizedList bruger sig selv som lås: synchronized (l) tager samme lås som dens metoder, og ingen andre kan komme ind mellem contains og add. Java-dokumentationen beder om det samme for at iterere: synchronized (list) { for (…) … }.

Samme eksperiment med 200 000 forsøg og synchronized (l): [1, 1] kom 0 gange.

Løsning 2: en ny metode i den thread-safe klasse

Pas på: på slide 79 er metoden skrevet public void synchronized. I Java kompilerer det ikke (rigtige meddelelser fra javac):

public void synchronized addIfAbsent(T e) { if (!l.contains(e)) l.add(e); }
error: <identifier> expected
error: '(' expected
error: invalid method declaration; return type required

Modifikatorerne (public, static, synchronized, final) skal stå før returtypen: public synchronized void addIfAbsent(…). Hvis du skriver det i hånden til eksamen, så pas på rækkefølgen.
