Sikker publicering og uforanderlighed

Punkt 3, 4 og 5 af tjeklisten: feltets startværdier skal være synlige for alle (safe publication), det der ikke ændrer sig, skal gøres uforanderligt (immutability), resten skal beskyttes (gensidig udelukkelse). Til sidst øvelse 4.2 (Person) gennemgået.

Safe publication

Tilstanden i en klasse er publiceret sikkert, hvis feltets startværdier, efter at et objekt er initialiseret, er synlige for enhver tråd, der tilgår objektet.

Det kræver, at initialiseringen happens-before publiceringen. Publicere = gøre referencen til objektet tilgængelig for andre tråde.

Kursets kode gentager testen 10 millioner gange, og kommentaren advarer om, at problemet på de fleste systemer ikke ses. JMM tillader det dog: til eksamen ræsonnerer man ud fra reglerne, ikke ud fra det, der kommer ud, når man kører.

Hvis referencen til objektet kommer ud under konstruktøren (f.eks. ved at sende this til en anden tråd), er problemet ikke safe publication, men det skal altid undgås.

Hvordan den gøres sikker

Slidene giver 4 måder for primitive typer og 3 for referencer. Hver virker kun under visse betingelser.

MådePrimitive (int…)Referencer (Object…)Hvornår den kan bruges
standardværdi0, falsenullhvis standarden er en god startværdi
volatileja—kun hvis feltet skal være volatile: ellers koster det ydeevne
finaljaja: den standard mådehvis værdien ikke længere ændrer sig (for en reference: referencen ændrer sig ikke, indholdet kan gøre det)
staticjajakun hvis feltet skal tilhøre klassen, ikke objektet
 
public class SafeInitialization {
    private int x;              // lasciato al default 0
    private final Object o;     // final
    public SafeInitialization() {
        x = 0;
        o = new Object();
    }
}

Slidene advarer: indtil nu var initialiseringen blevet ignoreret "for clarity and simplicity". Fra denne forelæsning af skal den tages i betragtning i øvelserne.

Uforanderlighed

  • Et uforanderligt felt ændrer ikke værdi efter initialiseringen. Tænk på det som en konstant.
  • final forhindrer at tildele feltet igen. Men en variabel af objekttype indeholder en reference: final blokerer referencen, ikke det objekt, den peger på.
  • Hvis det aldrig ændrer sig, kan data races kun findes under initialiseringen.

1) feltet kan ikke ændres efter publiceringen; 2) det er publiceret sikkert; 3) det slipper ikke ud.

Gensidig udelukkelse

Hvis tilstanden er foranderlig, skal hver adgang ske med den samme lås.

Øvelse 4.2 gennemgået: Person

Krav: id kan ikke ændres; zip og address ændres sammen; alle felter kan læses; konstruktør uden parametre (id = forrige + 1, den første er 0); konstruktør med startid (bruges kun, hvis det er den første person, der oprettes).

"The class state is id, name, zip, address, plus the static fields nextId and firstCreated. All fields are private and the getters only return primitives or immutable Strings, so no state escapes. The static fields are only accessed inside the static synchronized method assignId, which locks on Person.class: concurrent constructor calls are ordered by the monitor rule, so each gets a distinct id. id is final, so its initialization happens-before any access after the constructor finishes: other threads can never see a partially created Person. The other fields keep their default values until set, and every access to them holds the intrinsic lock of the object, so all conflicting accesses are ordered by happens-before. Hence there are no data races on the class state."

  • 4.2.4 Nej. En udførelse udforsker kun én interleaving ud af meget mange: en test kan vise tilstedeværelsen af en fejl, aldrig fraværet af den. Trådsikkerhed bevises ved ræsonnement (tjekliste + JMM), som i 4.2.2.

Målt på denne maskine, 3 tråde × 30 000 personer, med println inde i løkken (én pr. id, navn, zip, address). Med synchronized fjernet fra nextId, altså med data race'en inde: 0 dublerede id'er i 3 udførelser ud af 3. Testen ser ingenting.

Grunden: System.out.println tager en intern lås på strømmen. Trådene bruger næsten al deres tid i kø på den lås, så de udføres næsten én ad gangen, og to nextId overlapper aldrig.

Den samme kode uden synchronized, men med println uden for løkken og en enkelt kontrol til sidst (new Person().getId() skal være 90 000): den giver 52 900 – 58 300, i alle 5 udførelser. Med synchronized: 90 000, altid.

Det skal nævnes i 4.2.4: den samme forkerte kode "går igennem" eller "fejler" afhængigt af en detalje, der intet har med samtidighed at gøre. Derfor beviser en test ikke fraværet af data races.

Din People.java er korrekt: samme struktur (static synchronized nextId, final id, getter og setter synchronized). Person() kalder this(0): hvis det er den første person, er id = 0, som teksten beder om.

Skal rettes i de skriftlige svar. 4.2.2: du skrev "race condition free"; det rigtige ord er data race, og punkterne fra tjeklisten mangler (escaping, safe publication med final, lås på Person.class for konstruktøren). Spørgsmålet spørger udtrykkeligt hvorfor konstruktøren er trådsikker, og hvorfor man ikke ser halvt byggede objekter: svaret er final på id og metoden static synchronized. 4.2.4: svaret skal være et klart "nej", med begrundelsen (en test beviser ikke fraværet af data races).
