Synlighed, omordning, volatile

To måder, hvorpå den virkelige udførelse forråder intuitionen: en skrivning, som en anden tråd aldrig ser (synlighed), og instruktioner udført i en anden rækkefølge (omordning). Det er ikke "Java-problemer": det sker i ethvert sprog med samtidighed. volatile og låse er svarene.

Synlighed: skrivningen der ikke når frem

Hardware-intuition (slide 51): tråde kan køre på forskellige CPU'er. Uden synkronisering kan CPU'en beholde værdien i sine registre eller i sin cache, som de andre CPU'er ikke ser. Også JIT-compileren kan behandle læsningen som en konstant. Slidene advarer om, at hardware-forklaringen er vejledende: den præcise regel giver Java Memory Model (forelæsning 3).

En skrivning er garanteret synlig for en læsning kun hvis skrivningen happens-before læsningen. Uden en lås, volatile, start/join eller lignende mellem de to er der ingen garanti.

Ved at sætte synchronized(o) omkring læsningen i t1 og skrivningen i main (NoVisibility1Synchronized.java) afslutter programmet altid: main's unlock sker, før t1's efterfølgende lock, og denne rækkefølge gør skrivningen synlig.

Øvelse 2.2: MutableInteger, forklaret ordentligt

class MutableInteger {
    private int value = 0;
    public void set(int value) { this.value = value; }
    public int get() { return value; }
}
// t:     while (mi.get() == 0) { }
// main:  Thread.sleep(500); mi.set(42);

Du forklarede med JIT'en, at den "cacher værdien og omskriver løkken". Det er en mulig mekanisme, men til den mundtlige er det bedre at give kursets forklaring: der er ingen happens-before mellem skrivningen og læsningen, så synligheden er ikke garanteret; med synchronized på begge metoder (eller med volatile) findes rækkefølgen, og læsningen ser skrivningen. Så svaret afhænger ikke af, hvad en bestemt compiler gør.

"Making both get() and set() synchronized makes them use the intrinsic lock of mi. By the monitor rule, the unlock at the end of set(42) happens-before the lock at the beginning of any subsequent get(), so that get() is guaranteed to see the value 42 and the loop in t terminates."

Omordning: de instruktioner, der bytter plads

// PossibleReordering.java
x = 0; y = 0; a = 0; b = 0;
Thread one   = new Thread(() -> { a = 1; x = b; });
Thread other = new Thread(() -> { b = 1; y = a; });
one.start(); other.start();
one.join();  other.join();
System.out.println("(" + x + "," + y + ")");

Med synchronized forsvinder også (1,1): de to kroppe kører den ene efter den anden, og den der går først læser den anden's begyndelsesværdi 0. Ikke fordi låsen forhindrer omordning inde i tråden, men fordi gensidig udelukkelse forhindrer, at kroppene blandes.

volatile

volatile er et nøgleord for felter: volatile boolean running. Det er en svag form for synkronisering (slide 65): den løser synligheds- og omordningsproblemerne på den variabel, uden at blokere nogen. Netop fordi den ikke blokerer, kan den ikke forhindre to tråde i at blande sig i en sammensat operation.

  • En volatile-variabel bliver ikke gemt skjult i en CPU's registre eller caches: skrivningerne gøres synlige for de andre CPU'er.
  • Adgange til volatile-variable omordnes ikke.
  • Læsninger og skrivninger er ikke blokerende.
  • Den garanterer ikke gensidig udelukkelse: volatile int count; count++ er stadig en race condition.
