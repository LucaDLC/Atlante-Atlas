Kritisk sektion og lås

For at fjerne race condition'en er det nok at forhindre, at to tråde udfører sammen den del, der rører den delte hukommelse. Den del er den kritiske sektion; redskabet til at beskytte den er låsen.

Den kritiske sektion

En kritisk sektion er en del af det samtidige program, hvor samtidig adgang skal begrænses. Den skal dække de dele af koden, der bruger den delte hukommelse.

Nej. Det ville virke, men så ville en tråd lave alle sine gennemløb, mens den anden venter: programmet ville blive sekventielt, og du ville miste al fordelen ved trådene. Den kritiske sektion skal holdes så lille som muligt: kun adgangene til den delte hukommelse (øvelse 1.1.5).

Gensidig udelukkelse: de tre egenskaber (Dijkstra)

Problemet med gensidig udelukkelse (mutual exclusion problem) er: hvordan koordinerer man flere tråde, så en kritisk sektion udføres af én ad gangen? Dijkstra fastlagde de tre egenskaber, en ideel løsning skal have. De bruges til at vurdere enhver løsning, også dem du skriver i øvelserne.

Javas låse

lock()

Tager låsen, hvis den er fri. Hvis den tilhører en anden tråd, blokeres den, der kalder, indtil den frigives. Den er blokerende.

unlock()

Hvis der venter tråde, vækker den én, ellers frigiver den låsen. I alle tilfælde fortsætter den, der kalder. Den er ikke blokerende.

De er synkroniseringsoperationer: de fastlægger en rækkefølge mellem operationer fra forskellige tråde. Lock er en grænseflade; i kurset bruges implementeringen ReentrantLock.

Er denne interleaving mulig? (slide 59–60)

Typisk spørgsmål: bevis, at en interleaving ikke kan eksistere. Man ræsonnerer ved modstrid, uden at køre noget.

public void run() {
    l.lock();             // (1)
    int temp = counter;   // (2)
    counter = temp + 1;   // (3)
    l.unlock();           // (4)
}

Deadlock og try/finally-idiomet

Lås taget to gange

l.lock();
int temp = counter;
counter = temp + 1;
l.lock();   // blocca per sempre

Med en lås der ikke er reentrant venter tråden på sig selv. Rigtige fejl af denne slags findes i Linux-kernen.

Undtagelse med låsen i hånden

l.lock();
int temp = counter;
throw new Exception();
// unlock() mai eseguito

Tråden forlader uden at frigive låsen: alle de andre bliver blokeret for evigt.

Slidene: løsninger, der ikke bruger dette idiom, "cannot be deemed as free from deadlocks (note for assignments)". Brug det hver gang.

Kontrollér-derefter-handl: Covid-tornet (øvelse 1.3)

Højst 15 000 personer. Kontrollen og forøgelsen skal være i den samme kritiske sektion.

Forkert

if (counter < MAX_PEOPLE_COVID) {
    lock.lock();
    try { counter++; }
    finally { lock.unlock(); }
}

To tråde kan begge læse 14 999, bestå kontrollen og begge komme ind: 15 001.

Rigtigt

lock.lock();
try {
    if (counter < MAX_PEOPLE_COVID)
        counter++;
} finally {
    lock.unlock();
}

Mellem kontrollen og forøgelsen kan ingen anden tråd ændre counter.

Sådan forklarer man, at løsningen er korrekt (øvelse 1.1.4)

"The increment count = count + 1 is not atomic: it is a read followed by a write, so without synchronization some interleavings let a thread read a stale value and lose an update (a race condition). We made the read and the write a critical section protected by the same ReentrantLock, using the lock/try/finally idiom. Mutual exclusion guarantees that the operations of one thread's critical section cannot be interleaved with the other thread's, so every increment reads the value written by the previous one. Hence each of the 20 million increments adds exactly one, and the only possible output is 20,000,000."
