Classi thread-safe

Analizzare un intero programma concorrente con il JMM diventa impossibile oltre poche righe. Si analizza una classe alla volta. Questa pagina dà la definizione di classe thread-safe del corso e i primi due punti della checklist: class state ed escaping.

Correttezza e specifica

  • Un programma è corretto se rispetta la sua specifica.
  • La specifica è una frase precisa sul comportamento voluto. Esempi: "più lettori insieme, un solo scrittore e solo senza lettori"; "l'output deve essere PEOPLE*num_threads".
  • Nel corso le specifiche restano frasi (niente logica formale).

Ragionare su migliaia di righe (server, sistemi operativi, GUI) è ingestibile. In un linguaggio a oggetti si analizza la classe: restano solo le chiamate di metodo e gli accessi ai campi fatti in concorrenza.

La definizione del corso

"A class is thread-safe if no concurrent execution of method calls or field accesses (read/write) on objects of this class results in data races on the fields of the class."

In italiano: comunque si chiamino in parallelo i metodi (o si leggano/scrivano i campi) di un oggetto di questa classe, non c'è mai una data race sui campi della classe.

Nel corso "thread-safe" non vuol dire "sembra funzionare in concorrenza". Vuol dire solo: nessuna data race sui campi. La specifica di questa definizione è quindi "assenza di data race". È ispirata alla definizione del JMM: "a program is correctly synchronized iff none of its executions contains data races".

È diversa da Goetz cap. 4, che parla di invarianti della classe; somiglia a Goetz cap. 2, pag. 18.

"A concurrent program is thread-safe if and only if it is data race free." Non confondere: una classe thread-safe riguarda i suoi campi, un programma thread-safe riguarda tutte le sue variabili condivise. Goetz non definisce i programmi thread-safe.

Cosa garantisce

Nessuna data race sui campi della classe, per qualsiasi uso concorrente dei suoi metodi.

Cosa non garantisce

Nessuna race condition. Un programma che usa solo classi thread-safe può comunque sbagliare risultato: esempio in confinamento e azioni composte.

La checklist: 5 elementi

Per mostrare che una classe è thread-safe bisogna far vedere che, in qualsiasi esecuzione concorrente di accessi ai campi e chiamate di metodo con almeno una scrittura, le azioni sono ordinate da happens-before. In pratica si controllano sempre questi elementi.

"When asked to reason about the thread-safety of a class, you must always cover these elements." Una risposta che dice solo "i metodi sono synchronized" è incompleta. Le slide citano un teorema (letture opzionali): questi elementi insieme bastano a garantire la thread-safety.

1 · Class state

Lo stato di una classe sono i suoi campi. Sono le variabili condivise da proteggere quando la classe è usata da più thread.

La definizione parla solo dei campi della classe. Un oggetto che arriva da fuori come parametro non è stato della classe.

Meglio evitare metodi che prendono oggetti come parametro e li modificano: la classe non può garantire l'happens-before sulle azioni su quell'oggetto, perché altri thread lo usano come vogliono.

2 · Escaping

Lo stato non scappa (does not escape) se si può raggiungere solo attraverso i metodi pubblici della classe. Se scappa, un thread può usarlo senza la sincronizzazione prevista, e non si può più garantire l'happens-before.

Primo modo di scappare: un campo non private

Dichiarare private tutti i campi di tipo primitivo garantisce che vengano toccati solo dai metodi della classe.

Secondo modo: restituire un riferimento allo stato

private non basta se un metodo restituisce l'oggetto che fa parte dello stato.

Non scrivere metodi che restituiscono riferimenti a oggetti dello stato. Restituisci valori (un int, un elemento immutabile come Integer o String) oppure una copia.

"The class state is the field a. It escapes through get(), which returns a reference to the internal list: a thread can then call set on it without holding the lock, so that write and the write in set(…) are not ordered by happens-before. This is a data race on the class state, hence the class is not thread-safe."

HashSet.add fa "guardo se c'è → scrivo il nodo → size++" in tre passi separati: due thread possono guardare entrambi prima che uno scriva.

ConcurrentSkipListSet (sopra ConcurrentSkipListMap) fa il passo decisivo con un compare-and-set (CAS): "scrivi il nuovo nodo solo se il puntatore vale ancora quello che ho letto". È un'unica operazione atomica dell'hardware: se un altro thread ha cambiato qualcosa nel frattempo, il CAS fallisce e il thread ricomincia la ricerca, e questa volta trova la chiave già presente → add restituisce false. Per remove è uguale: il nodo si cancella con un CAS sul valore (da v a null), e un solo thread lo vince.

Il contatore viene aggiornato (addCount(±1), un LongAdder thread-safe) solo dal thread che ha vinto il CAS: niente duplicati, niente decrementi doppi. Verificato sul sorgente del JDK 26.
