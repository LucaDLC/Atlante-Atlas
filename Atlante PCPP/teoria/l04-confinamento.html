Confinamento e azioni composte

Un oggetto non thread-safe si può rendere sicuro chiudendolo dentro una classe thread-safe: instance confinement. Ma usare solo classi thread-safe non basta a evitare le race condition: le azioni composte vanno protette a parte.

Instance confinement

Instance confinement: incapsulare l'accesso a un oggetto non thread-safe dentro una classe thread-safe. L'oggetto è "confinato": nessuno lo raggiunge se non attraverso i metodi della classe.

Le synchronized collections: Collections.synchronizedList(l) restituisce un involucro in cui ogni metodo è sincronizzato, e la lista originale è accessibile solo da lì. Qualsiasi collezione si può rendere thread-safe così (synchronizedSet, synchronizedMap…).

Funziona solo se nessuno tiene un altro riferimento all'oggetto interno. Se dopo synchronizedList(l) qualcuno continua a usare l direttamente, quegli accessi non passano dal lock.

Classi thread-safe ≠ nessuna race condition

Prova tu: ogni chiamata a un metodo della lista sincronizzata è un passo atomico.

Ripetendo l'esperimento 200 000 volte (JDK 26), [1, 1] è uscito 8 volte. Raro, ma possibile: per questo un test che "passa" non dimostra niente.

Se "programma thread-safe" vuol dire senza data race (la definizione del corso), questo programma è thread-safe. Se volesse dire senza race condition, non lo sarebbe. Il commento nel codice del corso lo dice esplicitamente: dipende dalla definizione.

Azioni composte: estendere una classe thread-safe

Un'azione composta è una sequenza di chiamate di metodo o accessi ai campi che deve avvenire tutta in una sezione critica. Esempi tipici: check-and-set (controlla e poi modifica), iterazione, navigazione (per esempio contains seguito da un'azione).

Soluzione 1: usare il lock intrinseco della collezione

public void addIfAbsent(List l, Integer e) {
    synchronized (l) {
        if (!l.contains(e)) l.add(e);
    }
}

Funziona perché la lista di synchronizedList usa sé stessa come lock: synchronized (l) prende lo stesso lock dei suoi metodi, e nessun altro può entrare tra contains e add. La documentazione Java chiede la stessa cosa per iterare: synchronized (list) { for (…) … }.

Stesso esperimento da 200 000 prove con synchronized (l): [1, 1] uscito 0 volte.

Soluzione 2: un metodo nuovo nella classe thread-safe

Attenzione: nella slide 79 il metodo è scritto public void synchronized. In Java non compila (messaggi veri di javac):

public void synchronized addIfAbsent(T e) { if (!l.contains(e)) l.add(e); }
error: <identifier> expected
error: '(' expected
error: invalid method declaration; return type required

I modificatori (public, static, synchronized, final) vanno prima del tipo di ritorno: public synchronized void addIfAbsent(…). Se lo scrivi a mano all'esame, occhio all'ordine.
