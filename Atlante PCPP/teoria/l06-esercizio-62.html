Esercizio 6.2: read-write lock con CAS

Un lock che può essere tenuto da molti lettori insieme oppure da un solo scrittore, senza bloccare mai: ogni metodo prova e restituisce subito true o false. Tutto lo stato sta in un solo AtomicReference, cambiato con compareAndSet.

L'idea: un campo solo dice chi tiene il lock

Un read-write lock distingue chi legge da chi scrive: più lettori insieme non si danno fastidio (nessuno cambia niente), uno scrittore invece deve essere solo. Qui la versione "try" (try-lock): se il lock non si può prendere, il metodo non aspetta, restituisce false.

un ReaderListlo tengono i lettori nella listaaltri lettori, nessuno scrittore

Tutto lo stato è un solo riferimento. Per questo basta un CAS per cambiarlo: non c'è mai un momento in cui "metà" del lock è aggiornata.

Le classi che descrivono chi tiene il lock

compareAndSet(h, nuova) confronta riferimenti, non contenuti. Se un thread modificasse la lista sul posto (per esempio cambiando un next), il riferimento in holders resterebbe lo stesso: il CAS di un altro thread non si accorgerebbe del cambiamento e lo cancellerebbe (aggiornamento perso). In più chi sta leggendo la lista vedrebbe nodi a metà. Con nodi immutabili ogni cambiamento è un oggetto nuovo, quindi un riferimento nuovo, e il CAS lo vede. È la stessa regola di IntPair in CasNumberRange della lezione.

6.2.1 e 6.2.2 · Scrittore: writerTryLock e writerUnlock

La domanda da farsi è sempre: chi può cambiare lo stato tra la mia lettura e la mia scrittura?

In readerTryLock: chiunque (la lista è condivisa da tanti lettori, e uno scrittore può entrare). Serve il CAS. In writerUnlock, dopo aver controllato che il Writer è mio: nessuno, perché ogni metodo chiamato da un altro thread fallisce senza toccare holders (writerTryLock → false, readerTryLock → false, i due unlock → eccezione). Lo stato "Writer(io)" lo può cambiare solo il proprietario. Un set semplice basta; compareAndSet(h, null) funzionerebbe uguale e riuscirebbe sempre.

Il set(null) fa anche da rilascio nel senso della memoria: AtomicReference.set è una scrittura volatile, quindi tutto quello che lo scrittore ha scritto prima dell'unlock è visibile al prossimo thread che legge holders e prende il lock (happens-before). È quello che rende il lock utile per proteggere dati.

writerTryLock calls holders.compareAndSet(null, new Writer(current)). The lock is unheld exactly when holders is null, so the CAS checks that the lock is free and installs a Writer for the calling thread in one atomic step. If two writers try at the same time, only the first CAS succeeds: afterwards holders is no longer null, so the other CAS fails and returns false. It also fails if readers hold the lock (holders is a ReaderList) or if the caller already holds it, so the lock is not reentrant. There is no loop and no waiting, so the method never blocks. The Writer stores the owner thread, which writerUnlock needs.

writerUnlock reads holders once and checks that it is a Writer whose thread is the calling thread. Otherwise (null, a ReaderList, or another thread's Writer) it throws an IllegalStateException. If the check passes, it releases the lock with holders.set(null). This check-then-act is safe without a CAS because, while the calling thread holds the write lock, no other thread can change holders: writerTryLock fails because holders is not null, readerTryLock returns false when it sees a Writer, and writerUnlock and readerUnlock called by other threads throw. So the value cannot change between our get and our set. Moreover, set on an AtomicReference is a volatile write, so everything the writer did before unlocking happens-before the next thread that reads holders and acquires the lock.

6.2.3 e 6.2.4 · Lettori: readerTryLock e readerUnlock

Per lo scrittore c'è un solo stato buono: null. Se il CAS fallisce, il lock è occupato: la risposta giusta è false, subito.

Per il lettore gli stati buoni sono tanti: null, [R1], [R2 → R1]… Se il suo CAS fallisce perché un altro lettore è entrato o uscito, il lock è ancora disponibile per lui: rispondere false sarebbe sbagliato. Quindi riprova.

E se nel frattempo è entrato uno scrittore? Il lettore legge null e prepara [R]; W fa CAS(null → Writer(W)) e vince; il CAS del lettore (null → [R]) fallisce, perché holders non è più null. Al giro dopo il lettore legge il Writer e restituisce false. Corretto: il CAS confronta con esattamente lo stato su cui il lettore ha deciso.

readerTryLock is a CAS loop. It reads a snapshot h of holders; if h is a Writer it returns false. Otherwise h is null or a ReaderList, and it builds a new list with the calling thread in front of h, then tries holders.compareAndSet(h, newList). The CAS succeeds only if holders is still exactly the snapshot, so the decision was based on the current state and no concurrent update is overwritten. If it fails, another thread changed holders in the meantime. If another reader locked or unlocked, the lock may still be available, so the method retries. If a writer took the lock, the next iteration sees the Writer and returns false. Since a ReaderList is immutable, every change creates a new object, so the reference comparison in the CAS detects every change, and threads reading the old list are not affected. A CAS fails only when another thread succeeded, so the method is lock-free.

writerTryLock e writerUnlock: nessun ciclo, finiscono sempre in pochi passi (wait-free). readerTryLock e readerUnlock: ciclo CAS, un CAS fallisce solo se un altro thread ha cambiato la lista, cioè ha finito la sua operazione (lock-free). Vedi Wait-free, lock-free, obstruction-free.

Il principio: fotografia, copia nuova, CAS

Tutti i metodi del lock seguono la stessa ricetta. Funziona solo se ci sono tutti gli ingredienti: un solo riferimento, oggetti immutabili, un CAS che controlla la fotografia.

Due campi atomici separati

AtomicInteger readers + AtomicReference<Thread> writer. Il lettore vede writer == null; lo scrittore vede readers == 0 e si mette in writer; il lettore fa readers++. Dentro tutti e due. Ogni operazione è atomica, ma la regola "lettori oppure scrittore" lega due campi, e un CAS ne protegge uno solo.

Un solo riferimento

Lettori e scrittore stanno nello stesso holders. Il lettore e lo scrittore fanno CAS sullo stesso riferimento: se uno cambia lo stato, il CAS dell'altro fallisce e quello ricontrolla. È la soluzione di CasNumberRange della lezione: lower e upper dentro un solo IntPair immutabile.

Il CAS confronta riferimenti. "Stesso riferimento" vuol dire "stesso stato" solo se l'oggetto non può cambiare. Se un thread potesse modificare la lista sul posto, il riferimento resterebbe lo stesso, il CAS di un altro thread riuscirebbe lo stesso e cancellerebbe la modifica. In più, un oggetto con campi final pubblicato con un AtomicReference (che si comporta come un volatile) è visibile completo a chi lo legge.

6.2.5 · Test sequenziali

Un thread solo, nessuna concorrenza: si controlla che le regole del lock siano giuste. Ogni test crea il suo lock, così i test non dipendono l'uno dall'altro.

6.2.6 · Test parallelo: mai due scrittori insieme

Molti thread provano a prendere il write lock. Chi ci riesce lo segna in un contatore condiviso "quanti sono dentro adesso". Se entrando trova già qualcuno, è una sovrapposizione. Alla fine, quando tutti i thread hanno finito, le sovrapposizioni devono essere 0.

6.2.7 · Challenging: niente read lock doppio

1. Il CAS riesce solo se holders è ancora esattamente la lista h su cui ho fatto contains, e quella lista è immutabile: ho controllato proprio la lista che sostituisco. Se nel frattempo è cambiata, il CAS fallisce e ricontrollo.

2. Comunque solo il thread stesso può aggiungere o togliere se stesso dalla lista (readerTryLock e readerUnlock usano sempre Thread.currentThread()). Gli altri thread possono cambiare la lista, ma non la risposta a "current c'è?".

Con questa versione un test che prende due read lock dallo stesso thread lancia eccezione. Il test giusto diventa: assertTrue(lock.readerTryLock()); assertThrows(IllegalStateException.class, lock::readerTryLock);

The check contains(current) and the CAS are not one atomic step, but this is safe here. First, the CAS succeeds only if holders still refers to the same list we checked, and lists are immutable, so we check exactly the list we replace; otherwise the CAS fails and we check again. Second, only the calling thread itself can add or remove itself from the reader list, so other threads cannot change the result of contains(current).
