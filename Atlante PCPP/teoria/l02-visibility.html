Visibility, reordering, volatile

Due modi in cui l'esecuzione reale tradisce l'intuizione: una scrittura che un altro thread non vede mai (visibility) e istruzioni eseguite in un altro ordine (reordering). Non sono "problemi di Java": succede in ogni linguaggio con concorrenza. volatile e i lock sono le risposte.

Visibility: la scrittura che non arriva

Intuizione hardware (slide 51): i thread possono girare su CPU diverse. Senza sincronizzazione la CPU può tenere il valore nei suoi registri o nella sua cache, non visibili alle altre CPU. Anche il compilatore JIT può trattare la lettura come costante. Le slide avvertono che la spiegazione hardware è indicativa: la regola precisa la dà il Java Memory Model (lezione 3).

Una scrittura è garantita visibile a una lettura solo se la scrittura happens-before la lettura. Senza lock, volatile, start/join o simili tra le due, non c'è nessuna garanzia.

Aggiungendo synchronized(o) intorno alla lettura in t1 e alla scrittura nel main (NoVisibility1Synchronized.java) il programma termina sempre: l'unlock del main avviene prima del lock successivo di t1, e questo ordine rende visibile la scrittura.

Esercizio 2.2: MutableInteger, spiegato bene

class MutableInteger {
    private int value = 0;
    public void set(int value) { this.value = value; }
    public int get() { return value; }
}
// t:     while (mi.get() == 0) { }
// main:  Thread.sleep(500); mi.set(42);

Hai spiegato con il JIT che "mette in cache il valore e riscrive il ciclo". È un meccanismo possibile, ma all'orale conviene la spiegazione del corso: non c'è happens-before tra la scrittura e la lettura, quindi la visibilità non è garantita; con synchronized su entrambi i metodi (o con volatile) l'ordine esiste e la lettura vede la scrittura. Così la risposta non dipende da cosa fa un compilatore specifico.

"Making both get() and set() synchronized makes them use the intrinsic lock of mi. By the monitor rule, the unlock at the end of set(42) happens-before the lock at the beginning of any subsequent get(), so that get() is guaranteed to see the value 42 and the loop in t terminates."

Reordering: le istruzioni che si scambiano

// PossibleReordering.java
x = 0; y = 0; a = 0; b = 0;
Thread one   = new Thread(() -> { a = 1; x = b; });
Thread other = new Thread(() -> { b = 1; y = a; });
one.start(); other.start();
one.join();  other.join();
System.out.println("(" + x + "," + y + ")");

Con synchronized sparisce anche (1,1): i due corpi vanno uno dopo l'altro, e chi va per primo legge lo 0 iniziale dell'altro. Non perché il lock impedisca il riordino dentro il thread, ma perché la mutua esclusione impedisce di mescolare i corpi.

volatile

volatile è una parola chiave per i campi: volatile boolean running. È una forma debole di sincronizzazione (slide 65): risolve i problemi di visibilità e di riordino su quella variabile, senza bloccare nessuno. Proprio perché non blocca, non può impedire che due thread si mescolino dentro un'operazione composta.

  • Una variabile volatile non resta nascosta in registri o cache di una CPU: le scritture vengono rese visibili alle altre CPU.
  • Gli accessi a variabili volatile non vengono riordinati.
  • Letture e scritture non sono bloccanti.
  • Non garantisce mutua esclusione: volatile int count; count++ resta una race condition.
