Azioni ed esecuzioni

Visibility e reordering rendono il comportamento reale difficile da prevedere guardando l'hardware. Il Java Memory Model (JMM) dà regole a livello di linguaggio per dire quali esecuzioni sono valide. Si parte da tre parole: azione, esecuzione, program order.

Perché serve un memory model

  • L'hardware cambia da un computer all'altro: istruzioni diverse, gestione della memoria diversa.
  • Compilatori, runtime e CPU fanno ottimizzazioni (riordino, riscrittura del codice) che producono risultati "paradossali": il ciclo che non termina, l'output (0,0).
  • Il JMM è un insieme di regole: la JVM genera solo esecuzioni valide per quelle regole, su qualsiasi hardware. Così il programmatore può prevedere cosa succede.

Il comportamento "normale" che ti aspetti. Un'esecuzione concorrente è sequenzialmente consistente se 1) rispetta l'ordine delle istruzioni dentro ogni thread e 2) le operazioni sembrano avvenire in un istante, una alla volta. L'output (0,0) di PossibleReordering non è sequenzialmente consistente.

Garantirla per ogni programma costerebbe tutte le ottimizzazioni. Il JMM la garantisce solo per i programmi correctly synchronized (pagina sui data race).

Azioni: "chi fa cosa"

Un'azione è una coppia t(o): t è il thread, o l'operazione. Per esempio t1(1) = il thread t1 esegue l'operazione numerata (1).

Esecuzioni

Un'esecuzione è una sequenza di azioni σ = α1, α2, α3, …

Program order

Date due azioni a, b dello stesso thread, a viene prima di b nel program order se, eseguendo quel thread da solo, a verrebbe eseguita prima di b. È definito sul codice: i riordini di compilatore o CPU non contano.

Per ogni thread è un ordine totale: presa qualsiasi coppia di sue azioni, una delle due viene prima.
