Data race e correttezza

Nel JMM un programma è corretto se nessuna esecuzione ha data race. Per dimostrarlo servono ancora due ingredienti: le azioni in conflitto e i synchronization order. Poi si vede come un lock ordina le azioni, e perché volatile cambia le regole.

Synchronization order ed esecuzioni ben formate

L'ordine totale in cui avvengono le azioni di sincronizzazione di un'esecuzione. Deve rispettare la mutua esclusione (lock annidati correttamente) e l'happens-before. Un programma può averne più di uno: ogni esecuzione ne ha uno.

Un'esecuzione è ben formata se è coerente con program order, happens-before e synchronization order. La JVM produce solo esecuzioni ben formate.

PossibleReordering ha un solo synchronization order: m(start(t1)), m(start(t2)), m(join(t1)), m(join(t2)). I thread non hanno azioni di sincronizzazione proprie.

Azioni in conflitto e data race

Due azioni sono in conflitto se accedono alla stessa variabile non volatile e almeno una è una scrittura.

C'è una data race tra a e b se 1) sono in conflitto e 2) non sono ordinate da happens-before.

Un programma è correttamente sincronizzato se nessuna delle sue esecuzioni contiene data race. La JVM garantisce che tutte le sue esecuzioni sono sequenzialmente consistenti: niente più comportamenti paradossali.

Sistemare con un lock, e dimostrarlo

l = new ReentrantLock();   // (init(l))
x = 0; y = 0; a = 0; b = 0;
Thread one = new Thread(() -> {
    l.lock();     // (1)
    a = 1;        // (2)
    x = b;        // (3)
    l.unlock();   // (4)
});
Thread other = new Thread(() -> {
    l.lock();     // (5)
    b = 1;        // (6)
    y = a;        // (7)
    l.unlock();   // (8)
});
one.start();   // (start(t1))
other.start(); // (start(t2))

Prevedere i valori: la visibilità

Se a → b, l'effetto di a è visibile a b. Quindi si può dimostrare quali valori sono possibili.

La regola volatile

Se a è una scrittura su una variabile volatile e b una lettura successiva della stessa variabile, allora a → b.

  • Gli accessi a variabili volatile sono azioni di sincronizzazione ma non danno mutua esclusione: aumentano molto i synchronization order possibili.
  • Per definizione gli accessi a variabili volatile non sono mai in conflitto. Quindi non possono dare data race.

Con volatile a, b in PossibleReordering restano in conflitto solo gli accessi a x e y, già ordinati da start e termination rule: il programma è correttamente sincronizzato. Gli output possibili sono (1,0), (0,1), (1,1); (0,0) no.

Hai scritto che con count volatile c'è una data race tra le due scritture. Per la definizione del corso no: gli accessi a variabili volatile non sono in conflitto, quindi non ci sono data race e il programma è correttamente sincronizzato. Però la race condition resta: entrambi i thread possono leggere 0 e scrivere 1, quindi count può valere 1. È proprio il confronto chiesto dal 3.1.9: la versione con lock stampa sempre 2, quella volatile può stampare 1. Dettagli nell'esercizio 3.1 svolto.

La strategia in 6 passi (slide 48)

La strategia è un procedimento meccanico: non serve "intuire" dove sta il problema. Si parte dalle azioni, si aggiungono le coppie che valgono sempre (program order, start, termination), poi si guarda cosa dipende dall'esecuzione (chi prende per primo il lock, quale volatile viene letto dopo). Ogni caso diverso dà un insieme HB diverso; alla fine ogni domanda d'esame (data race? correttamente sincronizzato? che valori può stampare?) si risolve cercando percorsi in quegli insiemi.

  1. Identifica le azioni e classificale (variable access, synchronization, other).
  2. Scrivi le coppie del program order.
  3. Scrivi le coppie delle azioni di sincronizzazione: start, termination, monitor, volatile.
  4. Elenca i possibili synchronization order.
  5. Guarda quali coppie di happens-before cambiano tra un synchronization order e l'altro.
  6. Per ogni differenza, scrivi l'insieme happens-before corrispondente (come HB1, HB2).

Con quegli insiemi puoi: trovare data race, dimostrare che non ci sono (correttezza), prevedere i valori delle variabili.
