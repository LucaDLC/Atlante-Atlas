synchronized: lock intrinseci

In Java ogni oggetto ha già dentro un lock con una condition variable: il lock intrinseco (le specifiche Java lo chiamano monitor). Si usa con la parola chiave synchronized. Il punto delicato è capire quale oggetto fa da lock.

Blocco synchronized = lock + try/finally

In Java ogni oggetto ha già dentro un lock, detto lock intrinseco (o monitor lock). La parola chiave synchronized lo usa senza dover creare un ReentrantLock: prende il lock entrando in un blocco o in un metodo e lo rilascia uscendo. Fa la stessa cosa dell'idioma lock + try/finally, con meno righe e senza la possibilità di dimenticare l'unlock.

Con un Lock

Lock l = new ReentrantLock();
l.lock();
try {
    // sezione critica
} finally {
    l.unlock();
}

Con il lock intrinseco

Object o = new Object();
synchronized (o) {
    // sezione critica
}

Il lock di o si prende entrando nel blocco e si rilascia uscendo, anche con un'eccezione. Ed è rientrante.

Su un metodo: quale lock?

synchronized si può scrivere anche davanti a un metodo. Allora la domanda importante è: quale oggetto fornisce il lock? Dipende da se il metodo è d'istanza o static, e sbagliare questa risposta è l'errore dell'esercizio 2.3.

Esercizio 2.3: la classe Mystery

class Mystery {
    private static double sum = 0;
    public static synchronized void addStatic(double x) { sum += x; }
    public synchronized void addInstance(double x)      { sum += x; }
    public static synchronized double sum()             { return sum; }
}

Tutto è private e tutti i metodi sono synchronized: sembra sicura. Non lo è.

In questo programma no: main chiama sum() dopo t1.join() e t2.join(). Le ultime scritture dei thread vengono prima del join per la regola di terminazione (lezione 3), quindi la lettura vede i valori finali senza data race. In una classe usata da thread che leggono mentre altri scrivono, invece, servirebbe.

"A synchronized instance method locks this, the Mystery object, while a static synchronized method locks Mystery.class. Since t1 and t2 hold different locks, their executions of sum += x are not mutually exclusive, and the non-atomic read-modify-write on the static field sum can interleave and lose updates."
