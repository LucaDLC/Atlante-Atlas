Esercizio 3.1 svolto

CountingThreads: due thread incrementano count una volta. È l'esercizio che allena tutto il Java Memory Model. Qui è svolto un punto alla volta, seguendo la strategia in 6 passi; in fondo 3.2 e 3.3 in breve.

Il programma con le operazioni numerate

// main (thread m)
count = 0;                              // (init)
CountingThread t1 = new CountingThread();   // (new1)
CountingThread t2 = new CountingThread();   // (new2)
t1.start();                             // (start(t1))
t2.start();                             // (start(t2))
t1.join();                              // (join(t1))
t2.join();                              // (join(t2))
System.out.println("count=" + count);   // (p)

// run() di CountingThread (t1 e t2)
int temp = count;      // (1)
count = temp + 1;      // (2)

Nelle risposte usa la numerazione che vuoi, ma dichiarala. Qui t1(1) è la lettura di t1, t2(2) la scrittura di t2.

3.1.1 · Le azioni

AzioneTipo
m(init)variable access (scrittura di count)
m(new1), m(new2)other (creazione degli oggetti thread)
m(start(t1)), m(start(t2)), m(join(t1)), m(join(t2))synchronization
m(p)variable access (lettura di count)
t1(1), t2(1)variable access (lettura di count)
t1(2), t2(2)variable access (scrittura di count)

new1/new2 scrivono anche le variabili locali t1 e t2 del main: classificarle come variable access è accettabile, purché lo dici. Non sono condivise, quindi non cambiano l'analisi.

3.1.2 – 3.1.4 · Gli insiemi di coppie

Hai scritto l'ordine come catena di frecce (m(5) → m(6) → …). Un synchronization order è una sequenza (un ordine totale), non un insieme di coppie happens-before: scrivilo tra parentesi con le virgole, come nella slide 21.

3.1.5 · Dimostrare la data race

Hai scritto "there may be a race condition between…". Qui la parola giusta è data race tra conflicting actions: race condition è un'altra cosa (pagina lock). E il "count == 1" non dimostra la data race: la dimostrazione è mostrare che nessuna delle due frecce è nell'HB, cioè che dagli insiemi PO, S, T non esce un cammino tra le azioni di t1 e quelle di t2.

3.1.6 – 3.1.7 · Con un lock

// run()
l.lock();              // (0)
int temp = count;      // (1)
count = temp + 1;      // (2)
l.unlock();            // (3)   (con try/finally)

Nel 3.1.6 hai scritto le due catene complete t1 → t2 e t2 → t1 e parlato di "two different interleavings". La domanda chiede se nascono più happens-before set: la risposta è "sì, due", HB1 e HB2, ognuno con una coppia in più data dalla regola del monitor (unlock di uno → lock dell'altro).

Nel 3.1.7 hai elencato coppie dentro lo stesso thread (program order). Quelle c'erano già: la dimostrazione deve prendere le coppie in conflitto tra t1 e t2 e mostrare il cammino che le ordina, in HB1 e in HB2, come nei due passi qui sopra.

3.1.8 – 3.1.9 · Con volatile count

Hai risposto No e scritto che letture e scritture di una variabile volatile sono "synchronization actions". Tutte e due le cose vanno corrette: sono variable access, e la definizione di conflicting actions esclude le variabili volatile. Quindi nessuna data race. Il count == 1 che hai descritto è vero, ma è una race condition: è proprio il punto del 3.1.9.

"Yes, all executions are data race free. By definition in the Java memory model, accesses to volatile variables are never conflicting actions, and the only shared variable, count, is volatile. Therefore there is no pair of conflicting actions and hence no data race. This does not prevent the race condition: both threads may read 0 before either writes, so the program may still print count=1."

3.1.10 – 3.1.11 · Mutua esclusione con happens-before (challenging)

3.1.10 Mutua esclusione per questo programma: in ogni esecuzione vale t1(3) → t2(0) oppure t2(3) → t1(0). Cioè: la sezione critica di un thread finisce (unlock) prima che l'altro entri (lock).

3.1.11 Con il corpo in un while(true): ogni iterazione i di t1 ha azioni t1(0i) … t1(3i). Per qualsiasi iterazione i di t1 e j di t2, il synchronization order mette uno dei due lock prima dell'altro unlock; la regola del monitor dà t1(3i) → t2(0j) oppure t2(3j) → t1(0i), e con il program order tutte le coppie in conflitto delle due iterazioni risultano ordinate. Essendo vero per ogni coppia di iterazioni, nessuna esecuzione (anche infinita) ha data race.

3.2 · StringSet in breve

public synchronized int findOrAdd(String s) {   // lock(s) · (a) indexOf · (b) add · unlock(s)
    int ret = list.indexOf(s);
    if (ret == -1) list.add(s);
    return ret;
}
public int find(String s) { return list.indexOf(s); }   // (c) indexOf, SENZA lock
  • 3.2.1 In conflitto: t1(b) (add = scrittura) e t2(c) (indexOf = lettura). t2 non fa azioni di sincronizzazione sul monitor di s: le uniche coppie che collegano t1 e t2 passano dal main (start), e danno solo m(start(t1)) → … e m(start(t2)) → t2(c). Nessun ordine tra t1(b) e t2(c): data race, programma non correttamente sincronizzato.
  • 3.2.2 Con find synchronized, t2 fa lock/unlock sullo stesso monitor. Due casi: t1(unlock) → t2(lock) oppure t2(unlock) → t1(lock) (regola del monitor), quindi t1(b) e t2(c) sono sempre ordinate: correttamente sincronizzato. find può restituire 0 o -1 a seconda di chi entra prima: è una race condition, non una data race.
  • 3.2.3 La data race del 3.2.1 c'è in tutte le esecuzioni: la lista parte vuota, quindi add viene sempre eseguita, e nessun synchronization order introduce coppie tra t1 e t2.

3.3 · Il ciclo che può non finire, in breve

int x = 0;
Thread t1 = new Thread(() -> {
    while (x == 0) { }                 // (r) lettura di x, ripetuta
    System.out.println("t1: x=" + x);
});
t1.start();                            // (start(t1))
x = 42;                                // (w) scrittura
System.out.println("Main: x=" + x);
  • 3.3.1 Per impedire le esecuzioni infinite deve valere m(w) → t1(r) per una lettura di t1 che viene dopo la scrittura: la scrittura x = 42 deve happens-before una lettura del while, così quella lettura vede 42 ed esce.
  • 3.3.2 Non vale: l'unica regola che collega m e t1 è la start rule, m(start(t1)) → t1(r1). Ma m(w) viene dopo m(start(t1)) nel program order del main, e non c'è lock, volatile o join che leghi m(w) alle letture di t1. Nessuna esecuzione ha m(w) → t1(r).
  • 3.3.3 Dichiara volatile int x. m(w) è una scrittura su una variabile volatile; ogni lettura t1(r) del while che nell'esecuzione viene dopo m(w) è una "subsequent read": per la regola volatile m(w) → t1(r). Quella lettura vede 42 e il ciclo termina. In alternativa: lettura e scrittura dentro synchronized sullo stesso oggetto (regola del monitor).

La domanda chiede quale coppia deve essere ordinata, non tutto l'happens-before del programma: basta dire "la scrittura x=42 del main deve happens-before una lettura di x nel while di t1", e spiegare perché con quella coppia il ciclo termina.
