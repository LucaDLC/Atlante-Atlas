Esercizio 6.1: CasHistogram

Un istogramma lock-free fatto di AtomicInteger, usando solo get e compareAndSet, e un test che lo confronta con la versione sequenziale. Prima cos'è un istogramma, poi la classe, poi il test.

Cos'è un istogramma

Una fila di caselle (bin), ognuna con un contatore: serve a contare quante volte capita ogni cosa. L'interfaccia Histogram:

metodocosa fa
increment(7)+1 alla casella 7
getCount(7)il valore della casella 7
getSpan()quante caselle ci sono (nell'esercizio 30)
getAndClear(7)restituisce il valore della casella 7 e la rimette a 0

Histogram1

int[] e counts[bin] = counts[bin] + 1: leggi, poi scrivi. Perfetto con un thread solo; con più thread perde incrementi (race condition). Nel test fa da riferimento, usato da un solo thread.

CasHistogram

La stessa cosa, ma ogni casella è un AtomicInteger e l'incremento è un ciclo CAS: non perde niente anche con molti thread. È la classe sotto test.

6.1.1 · La classe

La regola dei campi final non vale solo per il riferimento counts: un thread che vede l'oggetto dopo il costruttore vede anche tutto ciò che si raggiunge da quel campo com'era alla fine del costruttore. Quindi vede l'array e i 30 AtomicInteger già creati, ognuno a 0. Le modifiche successive sono visibili perché ogni AtomicInteger si comporta come un volatile.

Variabili immutabili: il riferimento counts (final, mai riassegnato) e, di fatto, il contenuto dell'array: dopo il costruttore counts[i] punta sempre allo stesso AtomicInteger. Mutabili sono solo i valori dentro gli AtomicInteger: sono lo stato dell'istogramma.

i) No escaping: the state is the array counts and the AtomicInteger objects in it. The field is private, no method returns the array or one of its AtomicIntegers (they only return int values), and the constructor neither starts threads nor passes this to other objects. ii) Safe publication: counts is final, so any thread that obtains a reference to the object after construction sees the array and all AtomicIntegers initialised to 0. Later updates are visible because each AtomicInteger behaves like a volatile variable. Immutable: the reference counts and, in practice, the array contents (each slot always points to the same AtomicInteger). Only the values inside the AtomicIntegers change.

Con AtomicIntegerArray e incrementAndGet / getAndSet la classe è thread-safe, ma viola il testo: serve AtomicInteger, e si possono usare solo get e compareAndSet.

6.1.2 · getAndClear è atomico?

Il metodo fa due cose: get (legge il valore) e clear (lo rimette a 0). La domanda: un altro thread può infilarsi tra le due e far perdere qualcosa? Con il ciclo CAS no.

get, poi set(0)

v = c.get(); c.set(0); return v; Se T2 incrementa tra le due righe, set(0) cancella il suo incremento e nessuno lo restituisce: perso.

get, poi CAS(v, 0)

Il CAS azzera solo se il valore è ancora v. Altrimenti riprova. Niente si perde: si comporta come se get e clear fossero un'operazione atomica.

Yes. getAndClear reads the value and then calls compareAndSet(oldValue, 0), which writes 0 only if the bin still contains oldValue. If another thread changes the bin between the read and the CAS, the CAS fails and the loop retries. So when the CAS succeeds, the returned value is exactly the value that was replaced by 0, and no update can happen in between and be lost: the get and the clear take effect together at the successful CAS.

6.1.3 · Cosa fa il test

countFactors(p) dice in quanti primi si scompone p, ed è la casella da incrementare. Con i numeri da 0 a 9:

numeriscomposizionecasella
0, 1nessuna0
2, 3, 5, 7sono primi1
4, 6, 92·2, 2·3, 3·32
82·2·23

Istogramma risultante: casella 0 → 2, casella 1 → 4, casella 2 → 3, casella 3 → 1. Il test fa lo stesso con i numeri da 0 a 4999.

Provato mettendo Histogram1 (non thread-safe) nella parte parallela: ha passato 100 ripetizioni su 100. Ogni thread fa un solo incremento, e la barriera sveglia i 5000 thread quasi uno alla volta, quindi si scontrano di rado. È il test che chiede l'esercizio, ma è un buon esempio di "un test che passa non dimostra niente". Ogni ripetizione dura circa un secondo (creare 5000 thread costa): 20 ripetizioni bastano.

Il test va in app/src/test/java/exercises06/TestHistograms.java, con package exercises06;. In src/main JUnit non è disponibile (è una dipendenza testImplementation), e senza package Histogram1, che non è public, non si vede.
