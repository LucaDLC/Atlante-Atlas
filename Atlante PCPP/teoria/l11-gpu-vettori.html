Settimana 11 · Parallelismo oltre i thread

GPU e istruzioni vettoriali (SIMD)

Due modi di fare tante operazioni uguali insieme: migliaia di thread semplici su una scheda grafica (GPU), oppure una sola istruzione che opera su 4–16 numeri dentro un singolo core della CPU. Quando conviene l'uno, quando l'altro, quando nessuno dei due.

CPU e GPU: due progetti diversi

La CPU ha pochi core (per esempio 4) molto complessi: sono bravi a eseguire codice irregolare, con molti salti e decisioni. La GPU ha moltissimi core molto semplici (per esempio 2304 in una Nvidia RTX 2070, organizzati in 36 symmetric multiprocessor da 64 core ciascuno), pensati per fare la stessa operazione su tanti dati. Nasce per la grafica, che è algebra lineare, cioè moltiplicazioni di matrici; dal 2006 circa si usa anche per il calcolo scientifico (CUDA) e oggi per il machine learning.

Sommare due array è un'operazione O(N) e anche copiare i dati è O(N): il tempo di copia domina, e la GPU non conviene (la slide lo dice: l'addizione di array su GPU non vale la pena). Conviene quando c'è molto calcolo per ogni byte spostato, come nella moltiplicazione di matrici.

Il kernel: un thread per elemento

Sulla CPU si somma con un ciclo. Sulla GPU non c'è il ciclo: si lancia un thread per ogni elemento, ognuno esegue la stessa funzione con un indice diverso.

Griglia, blocchi, thread, warp

I thread sono organizzati in tre livelli. Un thread esegue il kernel una volta. Un blocco è un gruppo di thread (al più 1024), in 1, 2 o 3 dimensioni. Una griglia è un gruppo di blocchi. Dentro l'hardware i thread di un blocco sono eseguiti a warp: gruppi di 32 che eseguono la stessa istruzione nello stesso momento (un thread può «non partecipare» se un if o un while lo esclude).

Per le matrici si usano due dimensioni: riga e colonna del thread si calcolano come l'indice di prima, una volta per asse.

Moltiplicazione di matrici: dove la GPU vince

La moltiplicazione di due matrici N×N usa O(N²) dati ma O(N³) operazioni: molto calcolo per pochi dati. È il caso buono per la GPU. L'elemento C[r][c] è la somma dei prodotti della riga r di A per la colonna c di B.

Lancio: blocchi di 32×32 thread e una griglia grande abbastanza da avere almeno N×N thread. Il numero di blocchi per asse è la divisione arrotondata per eccesso: (N + 31) / 32. Per N = 96 servono 3×3 blocchi.

Rendere più veloce: ordine dei cicli e tiling

L'idea più sofisticata è il tiling: invece di scorrere righe e colonne intere, si calcola C a pezzi da sottomatrici (tile, per esempio 32×32 float = 4 KB) abbastanza piccole da stare nella cache L1 della CPU, o nella shared memory della GPU. Il numero di somme e prodotti non cambia, cambia l'ordine degli accessi.

Ordini di grandezza dalla slide (laptop): il ciclo C riordinato su un solo core arriva a 62 miliardi di operazioni in virgola mobile al secondo (grazie alle istruzioni vettoriali, vedi sotto); la GPU a 857 miliardi, 14 volte più della migliore CPU. Il massimo teorico della GPU della slide è 7465 miliardi.

Istruzioni vettoriali dentro un core (SIMD)

Oltre al parallelismo tra core e thread (MIMD: molte istruzioni, molti dati) c'è un parallelismo dentro un core: una istruzione vettoriale opera su 4–16 numeri in un colpo solo (SIMD: una istruzione, molti dati). Un vettore in questo senso è una piccola tupla di valori dello stesso tipo, e ogni posizione si chiama lane (corsia). Non è il vettore matematico (u₀, u₁, …): l'esercizio 11.3 distingue i due significati.

Il compilatore C può generare queste istruzioni da solo. In Java si usano esplicitamente con il pacchetto jdk.incubator.vector (modulo incubator: va aggiunto con --add-modules jdk.incubator.vector sia in compilazione sia in esecuzione). I tipi: FloatVector, ShortVector…, VectorMask, VectorOperators. Una species (VectorSpecies) descrive il hardware vettoriale per un tipo di dato: FloatVector.SPECIES_PREFERRED.length() è il numero ottimale di lane (provato su questo PC: 16 float, 32 short; sul Mac della slide: 4).

Questo ciclo assume che A.length sia multiplo del numero di lane: l'ultimo giro leggerebbe oltre la fine dell'array. Nell'esercizio 11.4 l'array di caratteri è riempito fino a un multiplo di 32 proprio per questo. Provato: la versione vettoriale e quella normale danno gli stessi risultati su un array di 32 elementi.

Elaborare testo con i vettori (esercizio 11.4)

I vettori funzionano anche sui caratteri. Non esiste un CharVector: si usa ShortVector, perché un char è un valore a 16 bit come uno short. Tre esempi, tutti compilati ed eseguiti.

Provato su un testo di prova (con array riempito a 64 caratteri): containsSimd trova '@' e non '#', countAZSimd conta 7 maiuscole, replaceSimd(…, 'o', '0') sostituisce tutte le 'o'. Le misure di tempo dell'esercizio (testo di 55 MB) non sono state eseguite.

Quando usare la GPU? (esercizio 11.1)

La domanda dell'esercizio è sempre la stessa: quanto calcolo c'è per ogni dato spostato, e i thread possono lavorare indipendenti? Le risposte sotto sono ragionamenti dall'idea della lezione, non una soluzione ufficiale.

La GPU è adatta a problemi con molto calcolo per dato (la moltiplicazione di matrici fa O(N³) operazioni su O(N²) dati), regolari (stessa operazione su ogni elemento, pochi salti) e indipendenti (poca sincronizzazione). Per poco calcolo per dato la copia host-device domina; per codice irregolare i warp restano a metà.

A GPU has thousands of simple cores that run the same kernel on many data elements, but it has its own memory, so the data must be copied between host and device. It pays off when there is much computation per byte transferred (like matrix multiplication, O(N³) work on O(N²) data) and the threads are independent. For O(N) work such as adding two arrays, the copy dominates. Inside a CPU core, SIMD vector instructions (FloatVector in Java) process 4–16 values per instruction and need no copy.
