Sezione critica e lock

Per togliere la race condition basta impedire che due thread eseguano insieme la parte che tocca la memoria condivisa. Quella parte è la sezione critica; lo strumento per proteggerla è il lock.

La sezione critica

Una sezione critica è una parte del programma concorrente in cui l'accesso concorrente deve essere limitato. Deve coprire le parti di codice che usano la memoria condivisa.

Mutua esclusione: le tre proprietà (Dijkstra)

Il problema della mutua esclusione (mutual exclusion problem) è: come coordinare più thread in modo che una sezione critica sia eseguita da uno alla volta? Dijkstra ha fissato le tre proprietà che una soluzione ideale deve avere. Servono per giudicare qualunque soluzione, anche quelle scritte da te negli esercizi.

ProprietàCosa garantisce
Mutual exclusional più un thread alla volta esegue la sezione critica
Absence of deadlocki thread prima o poi escono dalla sezione critica, lasciando entrare gli altri
Absence of starvationse un thread è pronto a entrare, prima o poi entra (in pratica non sempre si riesce a garantirla)

I lock di Java

lock()

Prende il lock se è libero. Se è di un altro thread, il chiamante si blocca finché non si libera. È bloccante.

unlock()

Se ci sono thread in attesa ne sveglia uno, altrimenti libera il lock. In ogni caso chi lo chiama continua. Non è bloccante.

Sono operazioni di sincronizzazione: stabiliscono un ordine tra operazioni di thread diversi. Lock è un'interfaccia; nel corso si usa l'implementazione ReentrantLock.

Questo interleaving è possibile? (slide 59–60)

Domanda tipica: dimostrare che un interleaving non può esistere. Si ragiona per contraddizione, senza eseguire niente.

public void run() {
    l.lock();             // (1)
    int temp = counter;   // (2)
    counter = temp + 1;   // (3)
    l.unlock();           // (4)
}

Deadlock e l'idioma try/finally

Lock preso due volte

l.lock();
int temp = counter;
counter = temp + 1;
l.lock();   // blocca per sempre

Con un lock non rientrante il thread aspetta se stesso. Bug veri di questo tipo esistono nel kernel Linux.

Eccezione con il lock in mano

l.lock();
int temp = counter;
throw new Exception();
// unlock() mai eseguito

Il thread esce senza liberare il lock: tutti gli altri restano bloccati per sempre.

Le slide: le soluzioni che non usano questo idioma "cannot be deemed as free from deadlocks (note for assignments)". Usalo ogni volta.

Controlla-poi-agisci: il tornello Covid (esercizio 1.3)

Al massimo 15 000 persone. Il controllo e l'incremento devono stare nella stessa sezione critica.

Sbagliato

if (counter < MAX_PEOPLE_COVID) {
    lock.lock();
    try { counter++; }
    finally { lock.unlock(); }
}

Due thread possono leggere entrambi 14 999, superare il controllo ed entrare tutti e due: 15 001.

Giusto

lock.lock();
try {
    if (counter < MAX_PEOPLE_COVID)
        counter++;
} finally {
    lock.unlock();
}

Tra il controllo e l'incremento nessun altro thread può cambiare counter.

Come spiegare che la soluzione è corretta (esercizio 1.1.4)

"The increment count = count + 1 is not atomic: it is a read followed by a write, so without synchronization some interleavings let a thread read a stale value and lose an update (a race condition). We made the read and the write a critical section protected by the same ReentrantLock, using the lock/try/finally idiom. Mutual exclusion guarantees that the operations of one thread's critical section cannot be interleaved with the other thread's, so every increment reads the value written by the previous one. Hence each of the 20 million increments adds exactly one, and the only possible output is 20,000,000."
