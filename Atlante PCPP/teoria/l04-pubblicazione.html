Pubblicazione sicura e immutabilità

Punti 3, 4 e 5 della checklist: i valori iniziali dei campi devono essere visibili a tutti (safe publication), ciò che non cambia va reso immutabile (immutability), il resto va protetto (mutual exclusion). In fondo, l'esercizio 4.2 (Person) svolto.

Safe publication

Lo stato di una classe è pubblicato in modo sicuro se, dopo aver inizializzato un oggetto, i valori iniziali dei suoi campi sono visibili a qualsiasi thread che accede all'oggetto.

Serve che l'inizializzazione happens-before la pubblicazione. Pubblicare = rendere il riferimento all'oggetto accessibile ad altri thread.

Il codice del corso ripete la prova 10 milioni di volte, e il commento avverte che sulla maggior parte dei sistemi il problema non si osserva. Il JMM però lo permette: all'esame si ragiona sulle regole, non su quello che esce eseguendo.

Se il riferimento all'oggetto esce durante il costruttore (per esempio passando this a un altro thread), il problema non è di safe publication, ma va evitato sempre.

Come renderla sicura

Le slide danno 4 modi per i tipi primitivi e 3 per i riferimenti. Ognuno funziona solo in certe condizioni.

ModoPrimitivi (int…)Riferimenti (Object…)Quando si può usare
valore di default0, falsenullse il default va bene come valore iniziale
volatilesì—solo se il campo deve essere volatile: altrimenti costa prestazioni
finalsìsì: il modo standardse il valore non cambia più (per un riferimento: non cambia il riferimento, il contenuto sì)
staticsìsìsolo se il campo deve essere della classe, non dell'oggetto
 
public class SafeInitialization {
    private int x;              // lasciato al default 0
    private final Object o;     // final
    public SafeInitialization() {
        x = 0;
        o = new Object();
    }
}

Le slide avvisano: finora l'inizializzazione era stata ignorata "for clarity and simplicity". Da questa lezione negli esercizi va considerata.

Immutabilità

  • Un campo immutabile non cambia valore dopo l'inizializzazione. Pensalo come una costante.
  • final impedisce di riassegnare il campo. Ma una variabile di tipo oggetto contiene un riferimento: final blocca il riferimento, non l'oggetto puntato.
  • Se non cambia mai, le data race possono esserci solo durante l'inizializzazione.

1) il campo non si può modificare dopo la pubblicazione; 2) è pubblicato in modo sicuro; 3) non scappa.

Mutua esclusione

Se lo stato è mutabile, ogni accesso va fatto con lo stesso lock.

Esercizio 4.2 svolto: Person

Richieste: id non modificabile; zip e address cambiano insieme; tutti i campi leggibili; costruttore senza parametri (id = precedente + 1, il primo è 0); costruttore con l'id iniziale (usato solo se è la prima persona creata).

"The class state is id, name, zip, address, plus the static fields nextId and firstCreated. All fields are private and the getters only return primitives or immutable Strings, so no state escapes. The static fields are only accessed inside the static synchronized method assignId, which locks on Person.class: concurrent constructor calls are ordered by the monitor rule, so each gets a distinct id. id is final, so its initialization happens-before any access after the constructor finishes: other threads can never see a partially created Person. The other fields keep their default values until set, and every access to them holds the intrinsic lock of the object, so all conflicting accesses are ordered by happens-before. Hence there are no data races on the class state."

  • 4.2.3 Eseguito una volta, il programma non mostra errori (la versione qui sopra: 400 000 id distinti su 400 000).
  • 4.2.4 No. Un'esecuzione esplora un solo interleaving tra moltissimi: un test può mostrare la presenza di un errore, mai la sua assenza. La thread-safety si dimostra con il ragionamento (checklist + JMM), come nel 4.2.2.

Misurato su questa macchina, 3 thread × 30 000 persone, con le println dentro il ciclo (una per id, nome, zip, address). Tolto synchronized da nextId, quindi con la data race dentro: 0 id duplicati in 3 esecuzioni su 3. Il test non vede niente.

Il motivo: System.out.println prende un lock interno sullo stream. I thread passano quasi tutto il tempo in fila su quel lock, quindi eseguono quasi uno alla volta e due nextId non si sovrappongono mai.

Stesso codice senza synchronized, ma con le println fuori dal ciclo e un solo controllo alla fine (new Person().getId() deve valere 90 000): esce 52 900 – 58 300, in tutte e 5 le esecuzioni. Con synchronized: 90 000, sempre.

Da citare nel 4.2.4: lo stesso codice sbagliato "passa" o "fallisce" a seconda di un dettaglio che con la concorrenza non c'entra. Per questo un test non prova l'assenza di data race.

Il tuo People.java è corretto: stessa struttura (static synchronized nextId, final id, getter e setter synchronized). Person() chiama this(0): se è la prima persona, id = 0, come chiede il testo.

Da sistemare nelle risposte scritte. 4.2.2: hai scritto "race condition free"; la parola giusta è data race, e mancano i punti della checklist (escaping, safe publication con final, lock di Person.class per il costruttore). La domanda chiede esplicitamente perché il costruttore è thread-safe e perché non si vedono oggetti a metà: la risposta è il final su id e il metodo static synchronized. 4.2.4: la risposta deve essere un "no" netto, con il motivo (un test non prova l'assenza di data race).
