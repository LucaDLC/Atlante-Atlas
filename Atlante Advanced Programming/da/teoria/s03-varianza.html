Varians: +A og −A

Varians besvarer ét enkelt spørgsmål: hvis en Kat er et Dyr, er en kasse med Katte så en kasse med Dyr? Det afhænger af, hvad man kan gøre med kassen: kun læse, kun skrive, eller begge dele.

Først: hvad "undertype" betyder

class Animal(val nome: String)
class Cat(nome: String) extends Animal(nome)

val a: Animal = Cat("Tom")   // ok: un Cat è un Animal

Man skriver Cat <: Animal og læser "Cat er en undertype af Animal": en værdi af Cat kan stå, hvor programmet forventer en Animal. Det modsatte gælder ikke: ikke ethvert Animal er en Cat.

Tag nu en generisk type T[A], for eksempel List[A]. Varians-spørgsmålet er: hvilken relation er der mellem T[Cat] og T[Animal]? Der er tre mulige svar.

SkrevetNavnHvis Cat <: Animal så…Sikkert, når containeren…
T[+A]kovariantT[Cat] <: T[Animal]producerer A (læses kun)
T[-A]kontravariantT[Animal] <: T[Cat]forbruger A (skrives kun)
T[A]invariant (standard)ingen relationlæser og skriver

Svarende i andre sprog (slide 12): + er out i C#, - er in. Java bruger wildcards ? extends og ? super.

Kovarians: sikker, hvis du kun læser

Hullet i Java-arrays

Java gjorde arrays kovariante, men arrays kan skrives. Det er eksemplet i 03-option/Variance.java.

Kovarians er kun sikker, hvis containeren producerer værdier (man læser dem). Kontravarians er kun sikker, hvis den forbruger dem (man sender dem ind). En container, der gør begge dele, skal være invariant.

Kontravarians: sikker, hvis du kun skriver

Compileren kontrollerer positionerne

Scala ser på hvor du bruger den type, der er erklæret med + eller -. En kovariant type kan ikke optræde som parameter (position "på vej ind"); en kontravariant type kan ikke optræde som resultat (position "på vej ud").

class Cell[+T](init: T):
  private var current = init
  def get = current
  def set(x: T): Unit = current = x
covariant type T occurs in contravariant position in type T of parameter x
Con +T la cella potrebbe diventare una Cell[Any] e ricevere un numero dentro una cella di stringhe. Il compilatore blocca set, dove T entra.
class Cell[-T](init: T):
  private var current = init
  def get = current
  def set(x: T): Unit = current = x
contravariant type T occurs in covariant position in type => T of method get
La slide 14 propone [-T], ma compilando con Scala 3.8 anche questo viene rifiutato: ora il problema è get, dove T esce. Una cella che si legge e si scrive può essere solo invariante: class Cell[T].

Hvorfor getOrElse har [B >: A]

Option[+A] er kovariant. Men getOrElse modtager en standardværdi: A ville havne i en indgangsposition.

=> foran B er noget andet: standardværdien beregnes kun, hvis den er nødvendig (uge 4).

Afstemning i forelæsningen

class A
class B extends A
val t: T[A] = new T[B]

Med hvilken erklæring af T kompilerer det? Svar: class T[+X] (kovariant). Man har brug for T[B] <: T[A] med viden om B <: A: samme retning, altså kovariant. Med de to andre siger Scala Found: T[B], Required: T[A] (kontrolleret).

"A type parameter is covariant if A <: B implies T[A] <: T[B]; it is safe when T only produces values of that type. It is contravariant if the relation is reversed, which is safe when T only consumes them. Mutable containers must be invariant, which is why Java's covariant arrays can fail at runtime with an ArrayStoreException."
