Rules and prohibitions

Every exercise sheet starts with the same sentence: "Do not use variables, side effects, exceptions or return statements (unless explicitly asked for)." The compiler does not stop you: var and return compile. The grade does.

"Unless explicitly asked for": in some exercises the text asks precisely for an exception. Example: tail, drop and init of week 2 must throw NoSuchElementException. There, it must be done.

The style scale (slide 11, week 2)

It is the grid the course uses to judge the code. Each row goes from left (worse) to right (better). "Always choose the best possible style for an exercise and your abilities."

Footnote to the slide: the rule holds "unless asked for explicitly, or really important for memory use". For example, tail recursion is used if it really is needed to avoid exhausting the stack.

From week 2: explicit recursion "smells"

"From now on, the use of explicit recursion is bad-smell for us. Only use explicit recursion when dealing with a non-standard iteration. Otherwise, you should use a suitable HOF. Similarly, you should only use fold if any of the other simpler HOFs cannot."

Order of choice: dedicated API (map, filter, exists…) → fold → recursion only if the iteration is unusual.

When the compiler fails you by itself

The course's project.scala compiles with -Werror: every warning becomes an error. So the file does not compile, and a homework that does not compile does not pass.

WarningTypical cause
match may not be exhaustivea case is missing, or all the cases have an if guard
Unreachable casea general case before a specific one
Unreachable case except for nulla case _ after cases that already cover everything

Academic honesty

  • During the course you may discuss the solutions, consult AI, paste pieces of code on the Discord.
  • You may not hand in solutions written by others, AI included, nor copy substantial parts. "You must type your hand-in yourself."
  • At the exam: no consulting other people, no AI of any kind.
