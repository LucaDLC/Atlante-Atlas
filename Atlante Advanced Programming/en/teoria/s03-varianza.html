Variance: +A and −A

Variance answers a single question: if a Cat is an Animal, is a box of Cats a box of Animals? It depends on what you can do with the box: only read, only write, or both.

First: what "subtype" means

class Animal(val nome: String)
class Cat(nome: String) extends Animal(nome)

val a: Animal = Cat("Tom")   // ok: un Cat è un Animal

One writes Cat <: Animal and reads "Cat is a subtype of Animal": a Cat value can stand where the program expects an Animal. The reverse does not hold: not every Animal is a Cat.

Now take a generic type T[A], for example List[A]. The question of variance is: what relation is there between T[Cat] and T[Animal]? There are three possible answers.

WrittenNameIf Cat <: Animal then…Safe when the container…
T[+A]covariantT[Cat] <: T[Animal]produces A (is only read)
T[-A]contravariantT[Animal] <: T[Cat]consumes A (is only written)
T[A]invariant (default)no relationreads and writes

Correspondences with other languages (slide 12): + is out in C#, - is in. Java uses the wildcards ? extends and ? super.

Covariance: safe if you only read

The hole of Java arrays

Java made arrays covariant, but arrays can be written. It is the example of 03-option/Variance.java.

Covariance is safe only if the container produces values (you read them). Contravariance is safe only if it consumes them (you pass them in). A container that does both must be invariant.

Contravariance: safe if you only write

The compiler checks the positions

Scala looks at where you use the type declared with + or -. A covariant type cannot appear as a parameter (position "going in"); a contravariant one cannot appear as a result (position "coming out").

class Cell[+T](init: T):
  private var current = init
  def get = current
  def set(x: T): Unit = current = x
covariant type T occurs in contravariant position in type T of parameter x
Con +T la cella potrebbe diventare una Cell[Any] e ricevere un numero dentro una cella di stringhe. Il compilatore blocca set, dove T entra.
class Cell[-T](init: T):
  private var current = init
  def get = current
  def set(x: T): Unit = current = x
contravariant type T occurs in covariant position in type => T of method get
La slide 14 propone [-T], ma compilando con Scala 3.8 anche questo viene rifiutato: ora il problema è get, dove T esce. Una cella che si legge e si scrive può essere solo invariante: class Cell[T].

Why getOrElse has [B >: A]

Option[+A] is covariant. But getOrElse receives a default value: A would end up in an input position.

The => in front of B is something else: the default is computed only if needed (week 4).

Poll of the lecture

class A
class B extends A
val t: T[A] = new T[B]

With which declaration of T does it compile? Answer: class T[+X] (covariant). One needs T[B] <: T[A] knowing B <: A: same direction, so covariant. With the other two Scala says Found: T[B], Required: T[A] (checked).

"A type parameter is covariant if A <: B implies T[A] <: T[B]; it is safe when T only produces values of that type. It is contravariant if the relation is reversed, which is safe when T only consumes them. Mutable containers must be invariant, which is why Java's covariant arrays can fail at runtime with an ArrayStoreException."
