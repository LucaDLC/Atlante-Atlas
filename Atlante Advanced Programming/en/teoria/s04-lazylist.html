LazyList

A LazyList has the same shape as a list, but head and tail are recipes that run only when someone asks for the value. That is why it can be infinite: only the piece you use is computed.

"It terminates because cons is non-strict in its tail: take(1000000000) only builds the first node and keeps the rest as an unevaluated thunk. drop(41) then forces 41 nodes, and take(10).toList forces 10 more. About 51 elements are ever computed; nothing is allocated for the remaining billion."

"toList is strict: it recurses until it meets Empty, which on an infinite list never happens. The recursion never returns, so it loops forever or overflows the stack."

takeWhile, forAll, exists

def takeWhile(p: A => Boolean): LazyList[A] = this match
  case Cons(h, t) if p(h()) => cons(h(), t().takeWhile(p))
  case _ => empty

def forAll(p: A => Boolean): Boolean = this match
  case Empty => true
  case Cons(h, t) => p(h()) && t().forAll(p)

def exists(p: A => Boolean): Boolean = this match
  case Empty => false
  case Cons(h, t) => p(h()) || t().exists(p)

&& and || are not strict: if the left part already decides the result, the right one is not computed. So forAll stops at the first element that fails, exists at the first that succeeds.

naturals.forAll(_ < 0) terminates? Answer: Yes, at once: false. 1 < 0 is false at the first element: && does not look at the rest (checked: false).

And naturals.forAll(_ >= 0)? Answer: No: it never finds a counterexample and runs out of stack. Every natural is ≥ 0, so it must check to infinity. The text says so: on infinite lists forAll and exists make sense only if you already know the answer.

"takeWhile builds its result with cons, one node at a time, so it never scans ahead. Only the ~150 elements that drop and take actually request are evaluated. The predicate is never false here, but that does not matter: nobody asks for more."

forAll { _ >= 0 }: "forAll stops only when it finds an element that fails the predicate. Every natural is ≥ 0, so it keeps recursing over an infinite list and overflows the stack."

forAll and exists on infinite lists: "On an infinite list forAll can only terminate by returning false, and exists only by returning true — so you may use them only when you already know the answer, and then you do not need them. On a finite list they always terminate, because in the worst case they reach the end."

Two lists of random numbers (slide 14)

lazy val random1: LazyList[Double] = Cons(() => Math.random, () => random1)
lazy val random2: LazyList[Double] = cons(Math.random, random2)

random1: direct Cons

The recipe () => Math.random is run again at each read: random1.take(2).toList gives different numbers each time.

random2: with cons

cons puts the head in a lazy val: computed once, then always the same.

Checked: two calls to random1.take(2).toList give different lists, with random2 the same ones. random1 is not referentially transparent because Math.random is an effect.

Why lazy lists

  • They separate the description of a calculation from its execution: the generator is the same whether 42 numbers or 1000 are needed.
  • Only what is needed is computed, as if everything were in memory.
  • lista.map(f).map(g) on a List goes through the list twice; on a LazyList zero times, until someone asks for the values.
  • They are functional iterators: in Java an Iterator is laziness with next() as the forcing.
