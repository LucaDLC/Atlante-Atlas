Assertions and contracts

Week 6, slides 1–14. Before testing a program one must say what "correct" means. One does it with true/false conditions on the program: assertions, pre-conditions (what the caller must guarantee), post-conditions (what the function guarantees), contracts and invariants. The next page has the computer check them on random inputs.

Assertions

An assertion is a Boolean condition on the state of the program (variables, values) that in correct executions is true. It is a sentence in Italian ("an empty list has length 0") turned into code that is worth true or false.

What they are for (slide 6): they help whoever reads the code (they say what is expected); they make the program fail at once, where the error arises (fail-fast); they help the compiler; they are the basis of testing and verification. Assertions are not only imperative: in FP they are used too.

"An assertion is a Boolean predicate over the program state (variables and values), usually expressed as a logical proposition, that evaluates to true in the correct executions."

The four flavours: require, ensuring, assert, assume

Scala has four ways of writing an assertion. At runtime they behave almost the same: if the condition is false they throw an exception. The difference is in the meaning: when one checks and whose fault it is if it fails. The image: a coffee machine. Pre-condition: "insert at least 50 cents" (if you do not, it is your fault). Post-condition: "a coffee comes out" (if you have paid and none comes out, it is the machine's fault).

Write small assertions: one violation at a time. If one single assertion checks five things, when it fails you do not know which of the five is wrong.

Pre-conditions: weaker and stronger

A pre-condition is a condition that, if it is true before running a piece of code, guarantees that the code behaves well. It is usually put at the entrance of a function and speaks of the arguments. A function can have many different pre-conditions that are all fine: what matters is how much they ask.

Post-conditions

A post-condition describes the correct result of a piece of code: it is checked after. For a function, it speaks of the returned value. In tests one does so: one calls the function, then one checks with an assertion that the result respects the post-condition.

Stronger = guarantees more. The strongest (strongest post-condition) describes the whole behaviour, but often writing it means rewriting the function. So one splits it into several weak post-conditions, and tests each. true as a post-condition says nothing about the result: the slides use it for nextInt, because saying more would mean describing the whole generator.

Contracts

A contract of a function is the pair pre-condition + post-condition. The caller must guarantee the pre at the moment of the call; the function, if the pre was true, must guarantee the post when it ends. If the pre was false, the function promises nothing.

Ideal contract

Pre weaker (I ask for the minimum) and post stronger (I promise the maximum). Hard to write everything.

In tests

One breaks it into many pieces: "if φ holds before, then ψ holds after", with stronger pres and weaker posts. Each piece becomes a test.

The weakest of all

false => true: it asks for nothing realisable and promises nothing. Every function that terminates respects it.

Invariants

An invariant is a property that must hold always, for an object or a data structure while the program runs. Two types in the slides:

  • Loop invariant: holds at each turn of a loop. Example: in insertion sort the elements to the left of the current index are already sorted. In FP there are no loops: its place is taken by the contract of the recursive function that replaces the loop.
  • Invariant of a data structure: holds for every value of that type. Example: in an AVL tree, at each node the heights of the two subtrees differ by at most 1. Or: "this list is sorted".
