Property-based testing

Week 6, slides 2 and 15–19. Scenario tests prove only the cases you imagined. Property-based testing (PBT) writes a law that must hold for all inputs, then proves it on many inputs generated at random with the ScalaCheck library. The contracts of the previous page become tests.

Scenarios against properties

The problem (slide 2): a scenario test (unit test) proves only the situations for which you wrote a test case, that is those you had foreseen. To cover a lot one needs many cases written by hand: it costs, and precisely the cases you did not think of remain out.

The solution: generate the test data automatically, at random but in a controlled way (with the generators, which we know how to make since week 5), and write the test as a property that must hold on all those inputs.

The PBT process (slide 17): 1. formulate the laws (thinking about pre, post and invariants helps); 2. generate random data; 3. test the laws on that data. It is closer to formal verification, but remains easy. It does not replace scenarios: they are used together.

forAll: the law proven on 100 inputs

forAll is the "for every" of mathematics (a quantifier). You give it a function that receives the inputs and returns a Boolean; ScalaCheck generates 100 random inputs and calls it on each. If it is always true, the test passes; at the first false it stops and shows you the input that made it fail (the counterexample).

Reading the output: counterexample and shrinking

When a property fails, ScalaCheck prints ! Falsified after N passed tests. and the arguments that made it fail: ARG_0 is the first parameter of the lambda, ARG_1 the second, and so on. Before printing them it shrinks them: it tries smaller versions and keeps the smallest that still fails. ARG_0_ORIGINAL is the counterexample as it was before.

Generators: Gen and Arbitrary

ScalaCheck has two key types. Gen[A] is a generator of random values of type A: the same idea as Rand[A] of week 5, and like Rand it has map, flatMap and therefore for/yield. Arbitrary[A] is the default generator of type A, the one that forAll looks for by itself among the givens when you write forAll { (x: A) => … }. When you test a new type, you write a generator for it; then you usually write many more tests than generators.

What a test file of the course is like

All the Exercises.test.scala files of the past weeks, and the exercise file of this week, are written like this. This week the role is reversed: the code (LazyList) is already there, and you write the test file.

Write tests for headOption, take, drop, map, append of the LazyList. The autograder runs them on broken versions of the LazyList (the mutants): the more mutants you make fail, the more points. The right version (lazyList00) must pass all your tests, otherwise you lose 35%.
