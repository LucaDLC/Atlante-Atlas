LazyList

Una LazyList ha la stessa forma di una lista, ma testa e coda sono ricette che si eseguono solo quando qualcuno chiede il valore. Per questo può essere infinita: si calcola solo il pezzo che usi.

take e drop

Un drop che su n <= 0 restituisce empty compila, ma è sbagliato: LazyList(1, 2, 3).drop(0) deve dare 1, 2, 3, non la lista vuota. Falliscono 5 test: Ex03.01, Ex03.02, Ex03.05, Ex04.01, Ex10.02 (anche Fibonacci, perché il suo test usa drop). Nel tuo file c'era proprio questa riga, ora corretta.

def drop(n: Int): LazyList[A] =
  if n <= 0 then LazyList[A] else …
missing argument list for method apply in object LazyList

  def apply[A](as: A*): adpro.lazyList.LazyList[A]

where:    A is a type variable
LazyList[A] è un tipo, non un valore. Scritto in mezzo al codice, Scala prova a chiamare il costruttore LazyList(…) e gli mancano gli argomenti. Il valore che serve è this: la lista su cui è stato chiamato drop.

"It terminates because cons is non-strict in its tail: take(1000000000) only builds the first node and keeps the rest as an unevaluated thunk. drop(41) then forces 41 nodes, and take(10).toList forces 10 more. About 51 elements are ever computed; nothing is allocated for the remaining billion."

"toList is strict: it recurses until it meets Empty, which on an infinite list never happens. The recursion never returns, so it loops forever or overflows the stack."

takeWhile, forAll, exists

def takeWhile(p: A => Boolean): LazyList[A] = this match
  case Cons(h, t) if p(h()) => cons(h(), t().takeWhile(p))
  case _ => empty

def forAll(p: A => Boolean): Boolean = this match
  case Empty => true
  case Cons(h, t) => p(h()) && t().forAll(p)

def exists(p: A => Boolean): Boolean = this match
  case Empty => false
  case Cons(h, t) => p(h()) || t().exists(p)

&& e || non sono strict: se la parte sinistra decide già il risultato, la destra non viene calcolata. Quindi forAll si ferma al primo elemento che non va, exists al primo che va.

naturals.forAll(_ < 0) termina? Risposta: Sì, subito: false. 1 < 0 è falso al primo elemento: && non guarda il resto (verificato: false).

E naturals.forAll(_ >= 0)? Risposta: No: non trova mai un controesempio e finisce la pila. Ogni naturale è ≥ 0, quindi deve controllare all'infinito. Il testo lo dice: su liste infinite forAll e exists hanno senso solo se sai già la risposta.

"takeWhile builds its result with cons, one node at a time, so it never scans ahead. Only the ~150 elements that drop and take actually request are evaluated. The predicate is never false here, but that does not matter: nobody asks for more."

forAll { _ >= 0 }: "forAll stops only when it finds an element that fails the predicate. Every natural is ≥ 0, so it keeps recursing over an infinite list and overflows the stack."

forAll ed exists sulle liste infinite: "On an infinite list forAll can only terminate by returning false, and exists only by returning true — so you may use them only when you already know the answer, and then you do not need them. On a finite list they always terminate, because in the worst case they reach the end."

Due liste di numeri casuali (slide 14)

lazy val random1: LazyList[Double] = Cons(() => Math.random, () => random1)
lazy val random2: LazyList[Double] = cons(Math.random, random2)

random1: Cons diretto

La ricetta () => Math.random viene rieseguita a ogni lettura: random1.take(2).toList dà numeri diversi a ogni volta.

random2: con cons

cons mette la testa in una lazy val: calcolata una volta, poi sempre uguale.

Verificato: due chiamate a random1.take(2).toList danno liste diverse, con random2 uguali. random1 non è referenzialmente trasparente perché Math.random è un effetto.

Perché le liste pigre

  • Separano la descrizione di un calcolo dalla sua esecuzione: il generatore è lo stesso sia che servano 42 numeri sia 1000.
  • Si calcola solo quello che serve, come se tutto fosse in memoria.
  • lista.map(f).map(g) su una List scorre la lista due volte; su una LazyList zero volte, finché qualcuno non chiede i valori.
  • Sono iteratori funzionali: in Java un Iterator è laziness con next() come forzatura.
