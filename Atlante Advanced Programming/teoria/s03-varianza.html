Varianza: +A e −A

La varianza risponde a una domanda sola: se un Gatto è un Animale, una scatola di Gatti è una scatola di Animali? Dipende da cosa si può fare con la scatola: solo leggere, solo scrivere, o entrambe le cose.

Prima: cosa vuol dire "sottotipo"

class Animal(val nome: String)
class Cat(nome: String) extends Animal(nome)

val a: Animal = Cat("Tom")   // ok: un Cat è un Animal

Si scrive Cat <: Animal e si legge "Cat è sottotipo di Animal": un valore Cat può stare dove il programma si aspetta un Animal. Il contrario no: non ogni Animal è un Cat.

Adesso prendi un tipo generico T[A], per esempio List[A]. La domanda della varianza è: che relazione c'è tra T[Cat] e T[Animal]? Ci sono tre risposte possibili.

Covarianza: sicura se leggi soltanto

Il buco degli array Java

Java ha reso gli array covarianti, ma gli array si possono scrivere. È l'esempio di 03-option/Variance.java.

La covarianza è sicura solo se il contenitore produce valori (li leggi). La contravarianza è sicura solo se li consuma (glieli passi). Un contenitore che fa entrambe le cose deve essere invariante.

Contravarianza: sicura se scrivi soltanto

Il compilatore controlla le posizioni

Scala guarda dove usi il tipo dichiarato con + o -. Un tipo covariante non può comparire come parametro (posizione "in ingresso"); uno contravariante non può comparire come risultato (posizione "in uscita").

class Cell[+T](init: T):
  private var current = init
  def get = current
  def set(x: T): Unit = current = x
covariant type T occurs in contravariant position in type T of parameter x
Con +T la cella potrebbe diventare una Cell[Any] e ricevere un numero dentro una cella di stringhe. Il compilatore blocca set, dove T entra.
class Cell[-T](init: T):
  private var current = init
  def get = current
  def set(x: T): Unit = current = x
contravariant type T occurs in covariant position in type => T of method get
La slide 14 propone [-T], ma compilando con Scala 3.8 anche questo viene rifiutato: ora il problema è get, dove T esce. Una cella che si legge e si scrive può essere solo invariante: class Cell[T].

Perché getOrElse ha [B >: A]

Option[+A] è covariante. Ma getOrElse riceve un valore di default: A finirebbe in posizione di ingresso.

Il => davanti a B è un'altra cosa: il default viene calcolato solo se serve (settimana 4).

Sondaggio della lezione

class A
class B extends A
val t: T[A] = new T[B]

Con quale dichiarazione di T compila? Risposta: class T[+X] (covariante). Serve T[B] <: T[A] sapendo B <: A: stesso verso, quindi covariante. Con le altre due Scala dice Found: T[B], Required: T[A] (verificato).

"A type parameter is covariant if A <: B implies T[A] <: T[B]; it is safe when T only produces values of that type. It is contravariant if the relation is reversed, which is safe when T only consumes them. Mutable containers must be invariant, which is why Java's covariant arrays can fail at runtime with an ArrayStoreException."
